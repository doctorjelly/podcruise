## How control reaches it

Not by call. There are no call sites anywhere in the image. The routine at
0x8008B580 loads the first sixteen bytes of run A four times and writes them to
0x80000000, 0x80000080, 0x80000100 and 0x80000180 — the processor's TLB-refill,
extended-TLB-refill, cache-error and general exception vectors — then flushes
and invalidates instruction cache over 0x80000000 for 0x190 bytes so the
processor will fetch the freshly written code. Run A is therefore executed at
whichever vector the processor selects; all it does is jump to run B, which lives
at its normal link address. Run B is entered only that way. Run C is entered only
from run B.

## State read and written

Processor state: reads and writes the status register, reads the cause register
and writes it back with a pending bit cleared on two paths, reads the exception
program counter and the faulting address, and rewrites the timer compare
register to acknowledge a timer interrupt. All of the general-purpose registers,
the multiply result pair, the floating-point control word and sixteen
floating-point registers are copied into memory.

## Recovered behavior

This is the whole exception and interrupt entry path.

The trampoline exists because the processor's exception vectors sit in a small
fixed window of low memory that the game's code does not occupy. It is
position-independent boilerplate: build the address of the handler and jump to
it. It is copied to all four vectors, so any exception the processor can raise
lands in the same handler.

The handler first has to save state before it can use any register freely, so it
parks the reserved pair on a fixed scratch area, records the incoming status
word there, drops the processor out of interrupt-enabled and exception-level
mode, and only then loads the running-thread pointer and copies the few values
it had to stage into that thread's own context. From there it saves the
remaining general registers, the multiply result pair, and — only if the thread
is marked as having used floating point — the floating-point control word and
the caller-saved floating-point registers. It rewrites the saved status word so
that the interrupt-enable bits the thread will resume with are the intersection
of what the thread had enabled and what the global permitted-interrupt mask
allows, and it does the same for the peripheral interrupt mask. It records the
exception program counter and marks the thread as no longer running.

It then classifies the exception from the cause code. Three cases are handled
specially and everything else is a fault.

For an interrupt, the handler enters a loop over the pending interrupt lines.
Each iteration takes the pending bits that are both asserted and enabled, folds
them into a small index, reads a byte from an index table and a code address
from a dispatch table, and jumps to the arm for the highest-priority line still
pending. Each arm acknowledges its source, posts the corresponding event, clears
its own bit from the working copy and branches back to the top of the loop, so
several simultaneous interrupts are serviced in one exception. The arms are:

- Timer: acknowledged by rewriting the compare register, then posts its event.
- Cartridge: switches to a private stack and calls an optional hook. If the hook
  is absent, or reports that it did not consume the event, the handler posts the
  cartridge event instead; if the hook consumed it, the handler goes straight to
  resumption.
- Peripheral controller: reads the peripheral interrupt register, masks it with
  the permitted set, and then walks its own sub-loop over six sources —
  signal processor, video, audio, serial, parallel and display processor — each
  acknowledged by the store its own hardware requires and each posting its own
  event. The signal-processor case distinguishes a normal completion from a
  break by inspecting two status flags and posts a different event for each.
  After the first source that leaves nothing else pending the sub-loop exits
  early.
- Shutdown warning: clears its own enable bit both in the saved context and in
  the head of the ready list, and posts its event exactly once — a latch in
  memory makes every later occurrence fall straight through to resumption.
- Two debug-port lines: no handler at all; the arms only clear the bit so the
  loop terminates.
- Two software lines: acknowledged by clearing the corresponding pending bit in
  the cause register, then posting their events.

When no enabled line is left pending, the handler falls into the resumption
epilogue. It compares the interrupted thread's priority against the head of the
ready list. If the interrupted thread is the lower priority, it is inserted into
the ready list in priority order; otherwise it is simply pushed onto the front,
which is cheaper and preserves its place. Either way control transfers to
func_8008D284, which selects and resumes a thread.

A breakpoint exception marks the thread with a fault flag, posts the
breakpoint event, and resumes.

A coprocessor-unusable exception is handled only for the floating-point unit
(run C): it turns on the coprocessor-enable bit in the thread's saved status
word, marks the thread as a floating-point user so that later exceptions will
save and restore its floating-point registers, and resumes it. A
coprocessor-unusable exception naming any other unit falls through to the fault
path.

Anything else is a fault: the handler records the offending thread in a
dedicated global, stops it, flags it as faulted, saves the faulting address, and
posts the fault event before resuming whatever else is runnable.

## Why this cannot come from C

The decisive instruction is at 0x8008CB1C: a coprocessor-0 read of the status
register into the kernel-reserved register k1. It disqualifies the body twice
over. A coprocessor-0 transfer has no C spelling at all, and the accepted
compiler has no inline assembly — it parses an `asm(...)` construct as a call to
an undeclared function, so there is no source text that reaches the instruction.
Separately, k0 and k1 are reserved for exception handlers by convention and no
compiler allocates them, yet this body depends on them being untouched across
the whole handler; the first instruction of the trampoline already writes k0.

Two structural facts confirm it independently. The trampoline is data as much as
code: another routine copies its bytes to a fixed low address, which requires
the sequence to be exactly four instructions long and position-independent, a
property no compiler will guarantee. And the handler is entered with no valid
stack pointer and leaves through a return-from-exception rather than a return
instruction, so it has no calling convention for a compiler to target.

## Note on translation unit

Runs A, B and C, together with func_8008D044, func_8008D12C, func_8008D22C,
func_8008D274, func_8008D284 and the two-instruction entry at 0x8008D400, form
one contiguous stretch of code from 0x8008CB00 to 0x8008D407 with no padding
anywhere inside it, and with alignment padding immediately before and
immediately after. The branch traffic between run B and run C, which crosses two
label boundaries in both directions with plain relative branches, cannot survive
separate assembly. They are one original assembly translation unit; see
`func_8008D044.md` for the full argument.
