# func_80016DD8

## Boundary

USA VRAM 0x80016DD8 - 0x80016F0B inclusive, ROM 0x179D8, size 308 bytes
(77 instructions). The body ends with the return instruction at 0x80016F04
whose delay slot at 0x80016F08 performs the final store, so the return value
slot is used productively. Six direct callers all target 0x80016DD8; no label
inside the range is reachable from outside. Boundary confirmed, not corrected.

## Callers

Six direct call sites, all inside the 0x8003A600-0x8003AAB0 region
(0x8003A638, 0x8003A69C, 0x8003A934, 0x8003A964, 0x8003AA80, 0x8003AAB0).

## Callees

None. The function is a leaf; the only stack traffic is a 16-byte frame used
for a local scratch array.

## Globals

None. All data is reached through the three pointer arguments.

## Recovered behaviour

The routine transforms a four-component single-precision vector by a
four-by-four single-precision matrix and writes the transformed vector to a
caller-supplied destination.

Argument one is the destination vector, argument two is the source vector and
argument three is the matrix, stored as four consecutive rows of four floats.

Each output component `k` is the sum of four products: element `k` of row zero
times component zero of the source, element `k` of row one times component one,
element `k` of row two times component two, and element `k` of row three times
component three. The four products are summed in that order, so this is the
row-vector convention (the source vector multiplies the matrix from the left).

All four components are computed into a private scratch vector first, and only
after the last one is finished are the four values copied out to the
destination. That ordering is observable: the destination is allowed to alias
the source vector, and callers do in fact pass the same buffer for both.

## Notes on shape

- Every product is written with the matrix element as the left operand. Writing
  the fourth term the other way round (source component first) produced a body
  that differed only in the order of two load instructions per component, which
  is what identified the intended operand order.
- The scratch vector is a genuine four-element local, not an artefact: the
  frame is exactly sixteen bytes and each component is stored and then read
  back before being written to the destination.
- The single no-operation instruction that appears between adjacent multiplies
  is the VR4300 multiply erratum workaround already in the accepted profile.

## Status

Exact in all four versions (usa, japan, europe, lrg_rev1).
