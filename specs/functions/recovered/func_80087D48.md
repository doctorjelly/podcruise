# func_80087D48 — whole-cache arm of func_80087CC0, not a function

## Verdict

Not a separate entity. `0x80087D48` is the "the caller asked for at least a
whole cache's worth" arm of `func_80087CC0`, given a label only because the
neighbour reaches it with a plain conditional branch and the label scanner
treats every branch target that follows a return as a new function. The
specification for this code belongs with `func_80087CC0`, where it is already
written up, and this file exists to record the classification.

## Boundary

- USA VRAM `0x80087D48` .. `0x80087D6B` inclusive, ROM `0x88948`, 36 bytes,
  nine instructions. The extent itself is right: the range ends with the return
  instruction and an empty delay slot, and a single padding word follows before
  the next real function at `0x80087D70`.
- What is wrong is the *kind* of thing the label names. The range is an arm of
  the neighbouring routine, not an entry point.

## Why this is an arm and not a function

Four checks, each independently sufficient:

1. **No caller.** There is no call instruction anywhere in the USA image that
   targets `0x80087D48`. The only control-flow edge that reaches it is one
   conditional branch inside `func_80087CC0`, taken when the requested byte
   count is not smaller than the whole cache.
2. **It consumes a value the neighbour computed.** The cache-size constant used
   to derive the sweep's stop address is never established inside this range.
   It is materialised by `func_80087CC0` a few instructions before the branch
   and is simply still live when the branch is taken. Entering at `0x80087D48`
   from any other place would leave that value undefined, so the address cannot
   be an entry point in any meaningful sense.
3. **It takes no arguments and returns on the neighbour's behalf.** The two
   arguments that `func_80087CC0` receives are untouched here; the range ends
   by returning through the link register the *neighbour's* caller supplied,
   which is how a tail arm ends, not how a callee that was never called ends.
4. **Both arms terminate the same call.** `func_80087CC0` has an early-out
   return of its own and a bounded-range walk that returns; this range is the
   third way out of that one call. Modelling it as a separate function would
   mean modelling a function whose prologue is somewhere else.

## Callers

None. One in-bound branch edge from `func_80087CC0` at `0x80087CD0`.

## Callees

None. The range makes no calls.

## Globals and access widths

None. It performs no data loads or stores of its own; it issues cache
maintenance operations against a fixed address window.

All four bodies were read independently and are word-for-word identical. In
each version the range sits immediately after its own parent, is entered only
by the parent's threshold branch, and is followed by a single padding word.

## Recovered behavior of the arm

When the caller of the parent routine asked to invalidate a range at least as
large as the entire data cache, walking the requested range line by line would
cost more than simply servicing every line the cache holds. This arm does the
latter: starting at the base of the cached view of memory, it visits every
cache line in turn, sixteen bytes apart, and for each one writes back any
modified contents and drops the line, stopping after the line that ends the
cache. It then returns to whoever called the parent routine.

Behaviourally this is the "give up on being selective" fallback of a
data-cache range invalidation primitive, and it discards more than the caller
asked for, which is safe because writing back first preserves anything dirty.

## Status

Skipped, permanently, and it should never have been queued as a function.

Two independent reasons no C source can produce these bytes. First, the loop
body is the processor's cache maintenance operation, which the accepted
compiler cannot emit from any C construct — there is no intrinsic, no library
call and no memory access that generates it, and the project rules forbid
inline assembly. Second, and more fundamental, this is not a compilation unit
at all: it has no entry, no parameters and no prologue, and it depends on a
register value established in a different labelled range.

Recommendation for the orchestrator: retire the `func_80087D48` symbol from the
decompilation queue and carry `0x80087CC0` .. `0x80087D6B` as one hand-written
assembly unit of 172 bytes (136 + 36) rather than as two.
