# func_8000E7F0

## Boundary

- USA VRAM `0x8000E7F0` .. `0x8000E8C3`, ROM `0xF3F0`, size 212 bytes (53
  instructions). Terminates with the return instruction at `0x8000E8BC` and an
  empty delay slot at `0x8000E8C0`.
- Boundary confirmed: the generated listing brackets the range with a matching
  label/endlabel pair, both direct call sites target `0x8000E7F0`, and no
  branch from the preceding function reaches into the range. Not corrected.

## Callers

Two direct call sites, both inside the same routine near `0x800104AC` and
`0x80010584`. Both push two extra arguments onto the outgoing stack area
(`0x14($sp)` and `0x18($sp)`) before the call, which corroborates the
seven-argument shape recovered below.

## Callees

- `func_8003EC40` (`0x8003EC40`) — takes the same seven arguments with the same
  widths; its own home-slot pattern (two sign-extended halfwords, four
  zero-extended bytes, one word) was used to confirm the parameter types.

## Globals and access widths

## Recovered behavior

The routine is a coordinate adapter placed in front of `func_8003EC40`. It
takes a horizontal and a vertical position expressed in whatever units the
current display mode uses, together with five pass-through arguments.

The current display width and height are held as the first two entries of the
global pair. The routine converts the incoming horizontal position and the
current width to floating point, divides one by the other to obtain a fraction
of the screen, and multiplies that fraction by 320 — the fixed horizontal
resolution the callee expects. The vertical position is rescaled the same way
against the second entry of the pair and a fixed height of 240.

Both rescaled values are truncated toward zero and narrowed to signed 16-bit
quantities, and the callee is invoked with those two normalised coordinates
followed by the five untouched arguments: four single-byte values and one
word-sized value that the caller supplied on the stack. Nothing is returned.

Matching detail: the two rescaled values must be produced as two ordinary
floating-point locals assigned before the call. Writing the two expressions
inline as call arguments computes the same result but schedules the two
integer-to-float conversions differently and does not reproduce the original
instruction order.

## Status

Exact in USA, Japan, Europe and lrg_rev1.
