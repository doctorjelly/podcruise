# func_80050208

## Boundary

- USA VRAM range: 0x80050208 .. 0x8005028C inclusive (0x88 = 136 bytes, 34 instructions).
- USA ROM offset: 0x50E08.
- Ends with a return whose delay slot is empty; the last real work is the
  final pass of a counted loop whose pointer advance sits in the branch
  delay slot just before the return.
- Assigned size 136 was correct; no boundary correction.

## Callers and callees

- Two distinct call sites in the USA build (each appears in both overlay
  listings). Both pass a single pointer and ignore any result; the register
  that would carry a second argument holds unrelated leftovers at one site,
  which confirms the function takes exactly one argument.
- No callees (leaf function).

## Globals and access widths

- None. The function writes only through its pointer argument.
- Fields touched, relative to the argument: a 32-bit word at 0x64, a 32-bit
  word at 0x68, single bytes at 0x6C..0x71, a 23-byte table starting at 0x72,
  and single bytes at 0x8E, 0x8F and 0x90.

The 136-byte Japan and Europe bodies are byte-identical to the USA body at
their mapped offsets. They therefore confirm both the structure and the
regional relocation without expanding the canonical matching scope.

## Recovered behavior

Resets one participant record to its start-of-event defaults. A 32-bit
progress word is cleared, the neighbouring 32-bit word is set to the
all-ones sentinel that the rest of the module uses for "no entry", and a
short run of byte-sized mode and count fields is loaded with fixed values
(one, zero, zero, zero, one, twelve). Three further byte fields near the end
of the record receive three, two and two.

The record then carries a 23-entry byte table, one entry per participant,
which is filled with the identity ordering: entry zero holds zero, entry one
holds one, and so on up to entry twenty-two. A sibling routine in the same
module swaps two entries of a similar table, so this is the unshuffled
starting order that later code permutes.

## Recovery notes

The emitted code fills the first three table entries with straight-line
stores, in descending entry order, and then runs a loop unrolled four ways
over the remaining twenty entries. Writing the whole table as one loop from
zero produces the same shape but forces the compiler to materialise fresh
copies of the constants one and two for the peeled entries, costing eight
bytes; writing the first three entries explicitly (in descending order, which
the compiler preserves) reproduces the original instruction sequence exactly,
including the unrolled loop and every store offset.

The original holds constants one and two in the third and fourth argument
registers. A bounded `decomp-permuter` search found an equivalent source shape
that recreates that allocation without changing the recovered behavior. The
assignment expression makes the peeled value two explicit, while two no-op
expressions preserve the compiler's live-range choices. Removing those
expressions shifts the constants down one register even though every opcode
and instruction position otherwise remains unchanged.

## Status

Byte-matching C for canonical USA. IDO 5.3 with the recorded `ido53_o2`
profile reproduces all 136 bytes exactly, including the empty `jr ra` delay
slot. The result was independently recompiled by the project verifier after
the permutation search. Japan and Europe were used only to confirm structure
and relocation.
