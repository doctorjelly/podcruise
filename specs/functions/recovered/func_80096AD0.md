# func_80096AD0 - buffer equality test

## Boundary

- USA VRAM `0x80096AD0` .. `0x80096BE8` inclusive; ROM `0x976D0` .. `0x977E8`.
- Size **284 bytes** (0x11C), not the 276 the label scan reported.
- The body ends with the return-jump at `0x80096BE4` whose delay slot at
  `0x80096BE8` loads the constant 1 into the integer return register. The word
  at `0x80096BEC` is a zero pad that aligns the next function to eight bytes.
- The heuristic label `func_80096BE4` is **not** a function. It has zero direct
  callers anywhere in the ROM and is the target of five conditional branches
  inside `func_80096AD0` (from `0x80096B08`, `0x80096B30`, `0x80096B6C`,
  `0x80096BA4`, `0x80096BCC`). It is the shared "operands differ" exit block.
  The assignment's corrected extent of 284 bytes is confirmed.
- The preceding function ends cleanly with its own return-jump and delay slot at
  `0x80096AC8`/`0x80096ACC`, so `0x80096AD0` is a genuine entry with no
  fall-through and no shared prologue.
- There is a second, earlier return site inside the body (`0x80096BDC` with its
  delay slot at `0x80096BE0`) that returns zero.

## Callers

One direct call site in the USA build, at `0x80091324`. It supplies a pointer
twelve bytes into a structure it holds, a pointer to a 32-byte scratch area on
its own stack, and the literal length 32, and it branches on whether the result
is zero. That confirms the third parameter is a signed count and the result is
an integer flag, not void.

## Callees and globals

None. The function is a leaf: it adjusts no stack frame, saves no
callee-saved registers, references no global data, and calls nothing.

## Parameters and result

1. left operand, a pointer to unsigned bytes,
2. right operand, a pointer to unsigned bytes,
3. a signed 32-bit byte count.

Result: 0 when the two ranges hold identical bytes, 1 at the first difference.
Both length tests in the body are signed (a signed "less than sixteen" test at
entry and a signed "greater than zero" test before the trailing byte loop), so a
zero or negative count yields 0 without touching memory.

## Recovered behavior

The routine is a length-parameterised equality test that widens its comparison
step whenever alignment permits.

- If the count is smaller than sixteen, it goes straight to a plain byte-by-byte
  loop; the fixed cost of the alignment machinery is not worth paying for short
  ranges.
- Otherwise it asks whether the two pointers are congruent modulo four, that is,
  whether they can ever be word aligned at the same time.
  - **Both operands share an alignment.** It computes how many bytes separate
    the left pointer from the next word boundary, deducts them from the
    remaining count, and compares just that leading fragment of both operands;
    if the fragments differ it reports inequality immediately. From there both
    pointers are word aligned, so it consumes as many whole words as the
    remaining count allows, comparing one aligned word from each operand per
    step and stopping at the first difference.
  - **The operands have different alignments.** Only one of them can be brought
    to a word boundary, and the routine chooses the right-hand operand: it
    compares the bytes up to that boundary one at a time, deducting them from
    the count. It then consumes whole words, reading the right operand as an
    aligned word and the left operand as a word-sized object with byte
    alignment, again stopping at the first difference.
- Whatever remains after the widened phase - always fewer than four bytes, plus
  everything when the count was short - is compared one byte at a time.
- Reaching the end of the trailing loop without a difference yields 0.

Each of the four loops is written so that the first element of the left operand
is read before the loop is entered and the read for the next iteration happens
at the bottom, which is what produces a rotated loop whose closing test
suppresses the speculative read on the final pass. All five difference exits
share a single return block.

## Status

`behavior`. The recovered C is behaviour-exact - it was checked against the host
C library's comparison routine over 400,000 randomised cases spanning every
combination of source alignment for both operands and lengths 0 to 79 - and it
reproduces the original's block structure, loop rotation, branch shapes and
widened comparison strategy. It compiles to 304 bytes against the original's
284.

### Why an exact match is not reachable from C

Twenty of the twenty-eight excess bytes come from one place: the leading
fragment comparison on the equal-alignment path. The original performs it with
six instructions that no C source can produce under this compiler, for three
independent reasons.

1. **It reads an undefined register on purpose.** The first instruction of that
   block copies a register that nothing has written since the function was
   entered - the entry is clean, there is no fall-through from the previous
   function, and no path reaches the block without passing through the entry.
   The copy exists so that the parts of the two comparison registers which the
   following partial reads do *not* touch hold the same bits, which makes the
   subsequent full-width difference test see only the freshly read fragment. A
   compiler cannot emit that: an assignment from an uninitialised local is dead
   and IDO 5.3 removes it. I confirmed this directly - a self-copy placed before
   a full-width read of the same variable is deleted from the output.
2. **It uses a left-partial word read with no right-partial partner.** Every
   unaligned access IDO 5.3 and 7.1 generate is a matched pair. I tried every C
   form that can produce one: a word member of a byte-aligned structure, a
   byte-aligned structure assignment, a two-byte-aligned structure, a 24-bit
   bitfield, a structure copy with a three-byte tail at a statically known
   offset, and reads whose low byte is provably discarded by a mask or a shift.
   All of them emit the pair; several add further instructions on top. The rest
   of the USA text agrees: every other left-partial access in the ROM has its
   right-partial partner three bytes along.
3. **The number of bytes it moves is a run-time quantity.** The fragment is one,
   two or three bytes depending on the pointer's alignment at the moment of the
   call, and a single instruction covers all three cases. No fixed-width C
   object can express a load whose width is decided at run time.

Taken together these are the signature of the hand-written byte primitives that
shipped with the platform's C library rather than of compiled game code. The
same signature appears on the routine at `0x80092850`, a range-fill primitive
which zeroes its own leading fragment with the mirror-image partial store after
the same "distance to the next word boundary" computation.

The remaining eight excess bytes are two scheduling differences that the missing
block's register pressure would plausibly absorb: one speculative
distance-to-boundary computation hoisted into a branch delay slot, and the
shared difference exit being laid out as a constant load plus a bare return
rather than a return with the constant in its delay slot.

### Reusable findings

- Writing the five difference exits as `goto` to one label at the end of the
  function keeps IDO 5.3 from unrolling the loops under the accepted profile;
  writing them as `return 1` lets the unroller fire and inflates the body from
  304 to 1096 bytes. No extra compiler flag is needed.
- Deducting the chunk length from the running count *before* the "is the chunk
  empty" test lets IDO put the subtraction in that test's delay slot, which is
  what the original does. Deducting it inside the guarded block costs a `nop`.
- A word-sized object with byte alignment is expressible to IDO 5.3 as a
  one-member structure under `#pragma pack(1)`. Reading such a member beside an
  ordinary aligned word read reproduces the original's interleaved
  partial-read/aligned-read sequence exactly, including the operand order.
- This IDO build accepts `-Wo,-loopunroll,0`, which suppresses unrolling but
  also suppresses loop rotation, so it is not a substitute for shaping the
  source.
