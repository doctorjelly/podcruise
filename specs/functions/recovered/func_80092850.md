## Recovered behaviour

The routine clears `length` bytes starting at `destination`. It is the classic
four-phase zero-fill:

1. **Short buffers.** If `length` is less than twelve, everything is done by the
   final byte loop; no alignment work is attempted.

2. **Head alignment.** Otherwise the routine computes how many bytes separate
   the destination from the next word boundary (zero when it is already
   aligned), subtracts that from the remaining count, clears exactly those
   bytes, and advances the destination to the boundary. The original clears
   them with a single partial-word store that writes from the destination up to
   the end of the word it lies in — see "Head store" below.

3. **Thirty-two byte blocks.** The remaining count is rounded down to a multiple
   of thirty-two and subtracted from the count. If that is non-zero, an end
   pointer is formed and a loop clears eight consecutive words per pass until
   the pointer reaches the end.

4. **Whole words.** What is left is rounded down to a multiple of four and
   subtracted. If non-zero, a second loop clears one word per pass up to its own
   end pointer.

5. **Trailing bytes.** Finally, while the signed remaining count is positive, an
   end pointer is formed and a byte loop clears one byte per pass.

The signed tests are visible in the original: the twelve-byte test and the final
positive test are both signed comparisons, whereas the two block guards test the
rounded counts against zero for equality.

## Head store — why this body does not reproduce byte-exactly

The head is cleared by one *partial* word store that writes only the bytes from
the destination up to the end of its containing word — a variable width of one,
two or three bytes decided by the destination's runtime alignment. This is the
single instruction that cannot be produced from C by the project's compilers,
and it is the whole reason the body is not exact.

Evidence gathered for this (all by compiling probe sources with the accepted
IDO 5.3 profile, and with IDO 7.1 for comparison):

- A four-byte store through any byte-aligned type — a byte-array struct, a
  `#pragma pack(1)` struct with a word member, a packed word bitfield — always
  emits **both** halves of the unaligned store pair, at every optimisation level
  from `-O0` to `-O3` and under both compiler versions. The pair is never split
  or shortened.
- When the compiler can prove the destination is word aligned it collapses the
  pair to an ordinary aligned store instead; it never keeps just one half.
- The compilers' block-move expander behaves the same way: copies of byte-array
  objects at every size from one to twenty-eight bytes, at known offsets one,
  two and three past a word boundary, and at sizes up to four kilobytes (where
  the expander emits a loop), always use paired partial-word instructions for
  each four-byte piece and plain byte stores for pieces of one to three bytes.
  The expander never emits an alignment prologue.
- The only unpaired partial-word instruction the compiler does emit is the
  *other* half of the pair, used for a trailing one-to-three byte piece of a
  copy whose start is known to be word aligned. That form is present elsewhere
  in this ROM (a nineteen-byte copy in `main_1A7B4`), which confirms the rule:
  the compiler emits an unpaired partial-word instruction only for a piece that
  *starts* at a word boundary, never for one that *ends* at one.
- Neither compiler expands the library block operations inline, with constant or
  variable length, so the head store cannot be a compiler-generated prologue.

A single "store the left part of the word" instruction is only correct when the
object runs from the address to the end of that word. With a compile-time known
alignment the compiler would have folded the offset into the instruction; with
an unknown alignment it must emit both halves. Neither case can produce the
observed instruction, so this store did not come out of a C compiler.

## Status

`behavior`. The submitted C is behaviour-equivalent and clears the same bytes;
it differs from the original by one instruction (the extra half of the unaligned
store pair) and by the register colouring of the block-count variable.

Closest byte agreement measured, using a plain aligned word store in the head
(undefined behaviour in C, so not submitted) under IDO 7.1 with
`-Wo,-loopunroll,0`: 21 of 39 instructions identical, first difference at offset
`0x18` — exactly the head store. Everything before it matches byte for byte.
Under IDO 5.3 the same source additionally colours the head count differently;
IDO 7.1 reproduces the original's colouring for the whole head sequence, which
is a small hint that this translation unit was built with a later compiler than
the accepted profile.
