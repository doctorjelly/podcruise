# func_8008E420

## Boundary

USA VRAM 0x8008E420-0x8008E54C, ROM 0x8F020, 300 bytes (75 instructions).
The body ends with a return instruction whose delay slot releases the frame,
so the boundary as assigned is correct. The preceding function ends with its
own complete return sequence at 0x8008E418/0x8008E41C, so nothing falls
through into this label, and every entry is a direct call. Frame is 0x18
bytes: sixteen bytes of outgoing-argument space plus one slot for the return
address; no callee-saved register is saved or restored.

The earlier report that this label is an out-of-line tail of func_8008E54C is
wrong on both counts: func_8008E54C sits *after* this function, and this
function is entered only by direct calls.

## Calling convention (the reason this looked hand-written)

This function takes all seven of its inputs in callee-saved registers and
destroys four of them without saving them. That is not the ordinary
convention, and it is why an earlier worker judged the body hand-written. It
is nevertheless ordinary compiler output. The original translation unit was
built one optimisation level higher than the rest of the ROM; at that level
the compiler allocates registers across all the functions of a unit at once,
so a file-local routine whose every call site is visible gets its parameters
wherever the allocator wanted them, may clobber registers the caller will
reload anyway, and is emitted with no ELF symbol at all. The matching unit
therefore locates the body by its offset within the unit's own text rather
than by name, and carries its own flag list.

Three facts settle this:

1. Compiling an ordinary seven-parameter file-local routine of this shape with
   the project's own compiler at the higher level reproduces the ROM body
   exactly - all 300 bytes, all 75 instructions. At the level used for the
   rest of the ROM the same source compiles to a completely ordinary function
   of a different length.
2. The two stores just after the frame adjustment land ten and twenty bytes
   above the incoming stack pointer. Those are the home slots of parameters
   five and six. Storing a parameter into its own home slot and immediately
   sign-extending it is the compiler's standard treatment of a narrow
   parameter that arrived in a register, and it pins parameters five and six
   as sixteen-bit signed values.
3. A sibling routine at 0x8008F0B4 in the same file takes one of its inputs in
   a *scratch* register that its callers hold live across the call. No
   hand-written routine would need that, and no ordinary caller could do it;
   only a whole-unit allocator produces it. Thirteen functions ROM-wide show
   this pattern, all inside the two library regions.

The three callers are all inside func_8008E54C, which is itself entirely
ordinary code with a full prologue, homed arguments and a fifth argument read
from the stack. The two are separate functions in the original source that
shared a translation unit; they are not one function.

## Callers

Three direct calls, all from func_8008E54C (0x8008E67C, 0x8008E7BC,
0x8008E8E8). Each call site materialises the seven inputs immediately before
the call and reloads its own scratch values from its frame afterwards; the
returned pointer is consumed every time.

## Callees

One indirect call through a function pointer read from the object at offset
0x30, taking three arguments and returning a value used as an address.

## Globals and access widths

No global data. The object passed in is read at offsets 0x14 and 0x18 as
32-bit words, 0x30 as a function pointer, 0x34 and 0x44 as 32-bit words, and
written at 0x40 as a 32-bit zero. The output buffer is written as pairs of
32-bit words at successive eight-byte slots.

## Regional addresses

Japan 0x8008F110 (ROM 0x8FD10), Europe 0x80093970 (ROM 0x94570),
lrg_rev1 0x8008E420 (ROM 0x8F020). Each regional body was read independently:
in every version the preceding function ends with its own complete return
sequence immediately before the entry, the entry instruction is the same
frame adjustment, and the body runs for the same 0x12C bytes. All three are
byte-identical to the USA body over the full 300 bytes - the function
contains no absolute address, so no relocation moved.

## Recovered behaviour

The function appends a short sequence of eight-byte command words to a growing
command buffer and returns the position just past the last one.

If the requested byte count is positive, it first asks the object's own
transfer routine, through the function pointer it carries, to stage that many
bytes; the routine hands back an address. The low three bits of that address
are the misalignment of the staged data, which is added to the byte count. Two
commands are emitted: one that selects the input location and a length rounded
down to a multiple of eight and then increased by eight, and one that loads the
staged block from the address rounded down to the same multiple. If the
requested count is not positive, no transfer is made and the misalignment is
taken as zero.

If bit one of the flag word is set, one further command is emitted carrying the
object's second recorded address, reduced to a physical address by masking off
the top three bits.

Two commands always follow. The first selects the input location advanced by
the misalignment, the output location, and a length of twice the sample count.
The second is the decode command itself: it carries the low byte of the flag
word and the object's first recorded address, again masked to a physical
address.

Finally the object's field at 0x40 is cleared and the new end of the command
buffer is returned.

## Source shape

Every command word in this function is a packed bit field: a code in the top
byte, sometimes a flag byte below it, and one or two sixteen-bit values at the
bottom. Two properties of how that packing is written decide the byte match,
and neither changes what the function computes.

1. Each field is written as "mask the value to its own width, then shift it
   into place", even where the shift alone would discard everything the mask
   removes. The redundant mask leaves no trace in the emitted code, but it
   changes the order in which the compiler evaluates the two halves of a
   packed word, and with it the order of the surrounding stores. Dropping the
   redundant mask on a single field cost twelve of the seventy-five
   instructions.
2. The three statements that make up one command - take the cursor and advance
   it, store the first word, store the second - occupy a single source line.
   The compiler orders statements partly by source line, so the same three
   statements spread over three lines schedule differently. Writing them as a
   one-line packing macro, the way a fixed command-list interface normally is
   written, is what closes the remaining fourteen instructions.

Neither the order of the parameters, the choice of local variables, the shape
of the cursor advance, the caller's shape, nor any compiler flag moves either
of these; they were each searched exhaustively before the two levers above
were found.

## Status

Exact. The USA body verifies byte-identical over all 300 bytes at the
canonical address, and Japan, Europe and lrg_rev1 verify byte-identical at
their own addresses from the same source. The compiled length is confirmed
independently of the config: the file-local body carries no ELF symbol, but
the next symbol in the unit begins exactly 0x12C bytes after the start of the
unit's text.
