## How control reaches it

By call, fourteen times, all from inside func_8008CB00 and from nowhere else in
the image. It is a private subroutine of the exception handler, not an exported
routine. Twelve of the fourteen sites pass their argument in the call's delay
slot; the other two rely on the argument already being set.

## Callees

func_8008D274 and func_8008D22C, each called once, on the path that wakes a
blocked thread.

## State read and written

Takes one argument: a byte offset into the event table at D_80149D00. The
callers use fifteen distinct values, all multiples of eight, one per event kind.

Reads: the event table at D_80149D00, whose entries are pairs of a destination
queue pointer and a preset message value. Through that pointer it reads and
writes the queue's occupancy count, its read cursor, its capacity, its slot
array and the head of its waiting-thread list.

Writes: one slot of the queue's message array, the queue's occupancy count, and
— by way of its two callees — the queue's waiting-thread list and the global
ready list at D_800A7BB8.

Register discipline: on entry it copies the incoming return address into a
callee-saved register and never restores that register's previous value. It
adjusts no stack pointer and reserves no frame.

## Recovered behavior

Posts one operating-system event to whichever message queue is currently
registered for it, without blocking and without failing loudly.

The argument selects a row of a small table that pairs an event with a
destination queue and a fixed message value. If no queue is registered for the
event, the routine returns immediately. If a queue is registered but already
full, it returns immediately as well, so an event that arrives faster than its
consumer drains it is dropped rather than overwriting anything.

Otherwise it computes the write position as the read cursor plus the current
occupancy, reduced modulo the capacity, stores the table's preset message into
that slot, and increments the occupancy.

Having made the queue non-empty, it checks whether any thread is blocked waiting
on that queue. If one is, it unlinks the first waiter and inserts it into the
global ready list in priority order. It does not switch to that thread; the
exception handler that called it decides when to resume, after all pending
interrupts have been serviced.

The division that produces the write position is a plain signed division and
carries the compiler's usual divide-by-zero and overflow traps with it. Those
traps are ordinary generated code and are not evidence of anything.

## Why this cannot come from C

**The reason recorded in the assignment does not survive the boundary
correction, and I am flagging that explicitly.** The corrected body contains no
coprocessor-0 transfer, no cache instruction, and no reference to either
kernel-reserved register — I scanned all 45 instructions for exactly those
classes and found none. Every privileged instruction in the assigned 232-byte
range lies in the 52-byte tail that actually belongs to func_8008CB00.

The corrected body is still not compiler output, but the decisive instruction is
a different one: at 0x8008D054 it copies the return address into the
callee-saved register s2, and at 0x8008D0F0 it returns by jumping through s2
rather than through the return-address register. Nothing saves s2 on entry and
nothing restores it on exit, so the routine deliberately destroys a register the
calling convention makes the callee's responsibility to preserve.

No C input reaches that. A compiler that needs the return address to survive
calls spills it to the stack and restores it, and it saves any callee-saved
register it uses; it cannot be persuaded to leak the clobber to its caller,
because the whole point of the convention is that it does not. This routine is
correct only because its fourteen callers are handwritten code in the same
source file that has already saved every register it cares about into a thread
context. It is a file-local subroutine that never had a C-visible signature at
all — it also reserves no frame while making calls, which is the same fact seen
from the other side.

Two supporting observations. Its callers keep live values in other callee-saved
registers across the call, which only works because those registers are shared
between caller and callee as a private arrangement. And its argument is a raw
byte offset into a table, pre-scaled by the caller, which is how handwritten
code indexes a table and not how a compiler passes an enumerated selector.

## Whether these bodies are one translation unit

They are, and this function is the clearest single piece of evidence. Four
independent facts:

1. **Interleaved control flow.** func_8008CB00's dispatch branches over this
   function's whole body into 0x8008D0F8, and that block branches back into
   func_8008CB00 twice. Those are relative branches with no relocation, so the
   source and target must be in the same assembler input. A separate object
   could not have produced them.
2. **No alignment anywhere inside.** The run from 0x8008CB00 to 0x8008D407 is
   continuous: func_8008D044, func_8008D12C, func_8008D22C, func_8008D274 and
   func_8008D284 each begin at the exact byte after the previous one ends, and
   four of those five entry addresses are not sixteen-byte aligned. Immediately
   before 0x8008CB00's run and immediately after 0x8008D407 there *is* alignment
   padding — one no-operation before 0x8008CAC0 and two after 0x8008D407,
   each bringing the next address to a sixteen-byte boundary. A linker aligns
   the start of every object's code; the pattern here is one aligned block with
   nothing aligned inside it.
3. **A calling convention that does not cross object boundaries.** This
   function's return through a callee-saved register, and its callers' reliance
   on that, is only sound if caller and callee were written together.
4. **Shared private state.** D_800A7BB8, D_800A7BC0, D_800A7B50 and the thread
   context layout are used by all four bodies and by nothing else in the
   region, and the transfers between them are one-way jumps rather than calls —
   func_8008D12C ends by jumping into func_8008D284, and func_8008CB00 does the
   same from three places. A never-return contract like that is not something
   two separately compiled units can agree on.

The unit's full extent is at least 0x8008CB00 .. 0x8008D407. It may start
earlier: func_8008CA80 and func_8008CAA0 immediately before it are also
handwritten coprocessor-0 code and belong to the same layer, and func_8008CAC0
between them and 0x8008CB00 fills its 64 bytes exactly with no padding. That
extension is plausible but I did not establish it, and it does not change the
answer for the four bodies in this assignment.
