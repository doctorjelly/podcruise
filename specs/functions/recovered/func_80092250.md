# func_80092250 — overlap-safe block copy (USA `main_91724.s`)

## Boundary

Assigned extent (label scan): `0x80092250`, 116 bytes.
Orchestrator's revised extent: `0x80092250`..`0x80092433`, 484 bytes.
**Both are short. The recovered extent is `0x80092250`..`0x80092553`, 772 bytes
(`0x304`), ROM `0x92E50`..`0x93153`.**

Evidence for the correction:

* The USA label scan produced three fragments — `func_80092250` (0x74),
  `func_800922C4` (0x170) and `func_80092434` (0x120). They are contiguous and
  sum to exactly `0x304`.
* Neither `func_800922C4` nor `func_80092434` has a single `jal` call site
  anywhere in the USA text. Each is reached only by a conditional branch from
  inside the preceding fragment (`0x80092294` reaches `0x800922C4`,
  `0x800923FC` reaches `0x80092434`), so both are internal branch targets, not
  entries.
* Control flow crosses the fragment seams in both directions: the third
  fragment's final stage branches backwards to `0x80092404`, inside the second
  fragment, and the second fragment's word stages branch back to `0x8009229C`,
  inside the first. A function boundary cannot sit inside a cycle.
* The Japan and Europe disassemblies, whose label scans did not split the body,
  already carry it as one function of `0x304` bytes (`func_80092F40`,
  `func_800977A0`). Their byte images are identical to the USA one over all 772
  bytes.
* The body is padded on both sides: one filler word before `0x80092250` and
  three after `0x80092553`, aligning the region to 16 bytes at both ends while
  neighbouring functions in the same file sit at 4-byte boundaries. The routine
  therefore occupies an object file of its own — the shape of a linked library
  member.

Last instruction of the body is a store executed in the delay slot of the
backwards branch that closes the final word stage; the two return points are at
`0x800922BC` and `0x8009242C`, each returning in its delay slot.

## Callers

Eight direct call sites, all in the two neighbouring translation units:
`0x8008A104`, `0x8008A118`, `0x8008AEC0`, `0x800911F8`, `0x800913B8`,
`0x800915F0`, `0x800921F0`, `0x80092A3C`. Observed argument patterns pass a
source pointer, a destination pointer and a small literal length (0x20, 0x100).
No caller consumes the returned value.

## Callees and globals

None. The body performs no call and touches no global; it reads and writes only
through its two pointer arguments.

## Access widths

Byte, halfword and word loads and stores through both pointers. Halfword
accesses occur only after the head fixup has brought both pointers to an even
address, and word accesses only after both are 4-byte aligned, so every access
is naturally aligned at run time.

## Recovered behavior

The routine copies a run of bytes from a source block to a destination block and
returns the destination pointer it was given.

It returns immediately, without touching memory, when the length is zero or when
the two pointers are equal.

It then decides a direction. If the destination lies below the source, or at or
above the end of the source run, the blocks cannot overlap destructively when
copied from low address to high, and the routine copies forwards. Otherwise the
destination starts inside the source run, and the routine copies backwards from
the end of both blocks. Either way the result is the same as if the source had
first been read out in full.

Within the chosen direction the routine uses a fast path only when the run is at
least sixteen bytes long and the two pointers share the same offset within a
four-byte word. That second condition is what makes wide transfers legal: if the
two pointers are congruent modulo four, one head fixup aligns both at once.

The head fixup moves one, two or three bytes — as one byte, one halfword, or a
byte plus a halfword, whichever the shared offset calls for — so that both
pointers reach a word boundary. The run is then drained in three descending
stages: whole blocks of thirty-two bytes as eight word transfers, then blocks of
sixteen as four, then single words, each stage repeating while enough bytes
remain. The backwards direction performs the mirror image of the same three
stages, walking downwards from the end.

Whatever the fast path leaves — always fewer than four bytes, and the entire run
when the fast path was skipped — is finished one byte at a time in the direction
already chosen.

The returned value is the destination pointer as it was received, saved before
any pointer is advanced.

## Status

**Cannot be recovered as C. The original is hand-written assembly.**

The decisive evidence is the trapping add instruction (`add`, not `addu`), which
appears three times in this body: once when the end of the source run is formed
for the overlap test, and twice when the two pointers are advanced to the end of
their blocks before a backwards copy. IDO's code generator emits the
non-trapping `addu`/`addiu` forms for every C-level addition, because C
addition must not trap. This was checked, not assumed:

* Twenty-two compiler and flag combinations that build were tried over probe
  files containing signed, unsigned, `long`, `short`, `char`,
  compound-assignment, array-subscript and pointer-offset additions, a byte copy
  loop and a word copy loop — IDO 5.3 and IDO 7.1, each at `-O0`, `-O1`, `-O2`
  and `-O3`, and with `-mips1`, `-ansi`, `-trapuv`, `-fullwarn` and
  `-Wo,-loopunroll,0`. (`-mips3` is rejected by both compilers in this
  installation.) Trapping arithmetic was produced zero times in every one.
* Across the whole USA text there are exactly eleven trapping arithmetic
  instructions. Three are in this body. The rest sit in the interrupt and
  exception handler region near `0x8008CD24`-`0x8008D4EC`, which also holds
  every coprocessor-0, TLB and cache instruction in the ROM, and in the
  signal-processor boot stub at `0x80097FF0`, which jumps into signal-processor
  address space. Both of those are hand-written assembly by construction.

The same value — source pointer plus length — is formed with the trapping form
at `0x80092268` and with the non-trapping form at `0x800922A4`, twenty-two
words apart in one body. No C source distinction exists that could select
between them, and no optimiser would choose differently for the same expression
in the same function.

A second, weaker sign points the same way: the comparison scratch register is
kept live across control-flow edges. At three sites the comparison for a later
stage is computed in the delay slot of a branch-likely and consumed only at the
branch target, with a duplicate copy planted on the fall-through path. IDO does
place comparisons in that register, but only within a single basic block; an
assembler macro expansion, the other way that register gets written, is always
contiguous by definition. Filling a likely-branch delay slot with the *next*
stage's test is a hand-scheduling idiom.

A third argument is compiler independent. Two words inside the body are
unreachable: `0x80092280` and `0x800923E4`. Each is a copy of the stage test
that the surrounding likely-branch delay slots already plant, each sits
immediately before a branch target, and neither carries a label, so nothing in
the ROM branches to it and no path falls into it — the word before `0x80092280`
is an unconditional branch's delay slot, and so is the word before
`0x800923E4`. A code generator does not emit unreachable instructions in the
middle of a function it just laid out; a hand-scheduled routine accumulates them
when fall-through copies are left behind after branches are turned into their
likely forms.

Secondary observations consistent with hand-written origin, none of them
conclusive on its own: two separate return sequences rather than a single shared
epilogue; seven delay slots left as fillers, three of them in the same six-word
stretch, where a compiler had material available to schedule; and both byte
loops emitted flat, with no unrolling and no remainder prologue, while the word
stages next to them run eight and four transfers wide. IDO unrolls a byte copy
loop four ways at `-O2`, so the flat form needs unrolling suppressed for the
whole translation unit — reachable with a per-unit flag list, which is why this
observation only corroborates rather than decides.

Optimisation-profile sweep, run against the corrected 772-byte target with a
scratch config (best compiled size, none matching): `-O0` 1792, `-O1` 1644,
`-O2` 988, `-O3` 988, `-O2 -Wo,-loopunroll,0` 848, `-O3 -Wo,-loopunroll,0` 848.
No per-unit flag list brings a C rendering within 76 bytes of the original, and
none can produce the trapping add at all.

`src/functions/func_80092250.c` holds a reviewed, behavior-correct rendering,
kept as documentation of what the routine does. It was validated on the host
against the platform's own overlap-safe copy over 18,670 cases — every
combination of source and destination alignment 0-7 and length 0-96, disjoint
and overlapping in both directions, plus lengths to 300 and the three
early-return cases — with no mismatch. It is not a match and must not be
substituted into the build; this function stays as assembly.
