# func_8008D22C

## Boundary

- USA VRAM range: 0x8008D22C .. 0x8008D270 inclusive (0x48 = 72 bytes, 18
  instructions).
- USA ROM offset: 0x8DE2C.
- Terminates with a return whose delay slot performs the last of the three
  stores, so that store belongs to this function.
- Assigned size 72 was correct; no boundary correction. The preceding function
  ends with an unconditional jump immediately before the entry, and the nine
  direct call sites all target the entry address.

## Callers and callees

- Nine direct call sites in the USA build.
- Leaf: no callees.
- Two arguments, both pointers; nothing is returned. Call sites confirm the
  arity: the third and fourth argument registers are never set up.

## Globals and access widths

- None. Only caller-supplied memory is touched. Link words at offset 0 and the
  owner pointer at offset 8 are 32-bit; the sort key at offset 4 is read as a
  signed 32-bit word and compared with a signed comparison.

## Recovered behavior

Inserts a record into a singly linked list that is kept in non-increasing order
of a signed sort key stored at offset 4 of each record.

The first argument is the address of the head cell, the second the record to
insert. The key of the incoming record is read once. The routine then walks the
chain with a trailing cursor that starts aimed at the head cell itself, and
advances for as long as the record under inspection ranks at least as high as
the incoming one; it stops at the first record that ranks strictly lower. The
incoming record is then spliced in ahead of that record: it takes over the
cursor's current link value, the cursor is pointed at it, and the incoming
record records the head cell it now belongs to at offset 8.

There is no null check inside the walk, so the list is required to end in a
sentinel record whose key is lower than any real key; the callers observed pass
fixed head cells that are set up that way. Inserting after equal-ranked records
makes the order first-in-first-out among equals.

## Compiler profile and the residual difference

The neighbouring function func_8008CAC0 proves this translation unit was built
at optimization level 1 (level 2 turns the loop branches into branch-likely
form, which neither original does). At level 1 the recovered source reproduces
this body's instruction sequence exactly, one operation at a time, including
the rotated loop, the single hoisted key load, the reload of the link word
after the walk, and the trailing store placed in the return delay slot.

Two artefacts remain and both trace to the same cause: the original body holds
its three working values purely in the code generator's expression temporaries
and reserves no stack frame at all, whereas every source shape that keeps three
values live across the loop gives them named register-class locals. Named
locals are given home slots at this optimization level, which adds the eight
bytes of stack adjustment the original lacks, and they are allocated out of the
argument registers instead of the high temporaries. Ten source shapes were
tried, including a pointer-to-link cursor, a hoisted key, K&R parameter syntax,
declaration reordering, both compiler versions available, every debug level,
and level 0 through level 3. None removes the frame while keeping three live
values, because the frame is a direct function of the number of declared locals
(measured: one or two locals give eight bytes, three give sixteen, none give
none). Reaching zero locals with two independently advancing pointers is not
expressible in C, so this body was most likely hand-written, or built by a
compiler revision that is not available here.

The compiled result is otherwise the same 72 bytes at the accepted level 2 and
the same instruction sequence at level 1; the differences are register naming
and the redundant frame adjustment only.
