# func_8001723C — build the rotation block of a 4x4 transform from three angles

Proposed merged specification document: `specs/functions/matrix_from_euler.md`.

## Boundary

- USA VRAM `0x8001723C` .. `0x8001734B` (inclusive), ROM `0x17E3C`, size 272 (0x110) bytes.
- Terminates with a return instruction whose delay slot is empty; the following
  label `func_8001734C` begins a distinct function with its own frame setup.
- The preceding function (`func_80016F0C`) ends at `0x80017238` with its own
  return; no branch anywhere in the image targets an address inside this range,
  so the assigned boundary is correct. `boundary_corrected: false`.

## Callers

Two direct callers, both in the same translation unit: `func_8001745C` and
`func_800174B8`. Both pass a matrix pointer plus three single-precision angles.

## Callees

`func_80014CC0`, called three times. Its contract, read at its own body and at
the independent call site in `func_80014D20`: argument 1 is a single-precision
angle in degrees, argument 2 is the address of a float that receives the sine of
that angle, argument 3 is the address of a float that receives the cosine.
(`func_80014CC0` scales its argument by a stored double ratio, then calls the
sine routine for the second output pointer and the cosine routine for the first;
`func_80014D20` divides the first output by the second, i.e. it forms a tangent,
which independently confirms the sine/cosine ordering.)

## Globals

None. The function touches only its arguments, its own frame, and the memory
addressed by argument 1.

## Frame

64-byte frame. Ten single-precision locals are laid out in declaration order
from the top of the local area downwards; only the first six are addressed. The
remaining four are the multiplication temporaries and stay in registers, but
they still consume the top-of-frame reservation, which is why the frame is
16 bytes larger than the six addressed locals require.

## Recovered behavior

Argument 1 addresses a sixteen-element single-precision matrix stored row by
row; arguments 2, 3 and 4 are three angles. The function asks the sine/cosine
helper for the sine and cosine of each angle in turn, forms the four products of
a first-angle factor with a third-angle factor, and then writes the nine
elements of the upper-left three-by-three block:

- element (0,0): first cosine times third cosine, minus the product of the two
  sines times the second sine.
- element (0,1): first cosine times third sine, scaled by the second sine, plus
  first sine times third cosine.
- element (0,2): the negated third sine times the second cosine.
- element (1,0): the negated first sine times the second cosine.
- element (1,1): first cosine times second cosine.
- element (1,2): the second sine.
- element (2,0): first sine times third cosine, scaled by the second sine, plus
  first cosine times third sine.
- element (2,1): the product of the two sines, minus first cosine times third
  cosine scaled by the second sine.
- element (2,2): third cosine times second cosine.

The three remaining elements of each row, the whole fourth row and the fourth
column are left untouched; both callers set them before calling. The resulting
block is orthonormal, so the three angles are a proper Euler triple and the
routine is a rotation constructor with the second angle applied about the axis
whose row is the plain sine/cosine row.

## Status

Behaviour recovered and reviewed. The compiled output is word-for-word identical
to the original for all 66 non-empty instructions, but the original image places
an empty instruction between two consecutive floating-point multiplications and
the locally available compiler does not. Two such empty words are missing, at
byte offsets `0x68` and `0x70`, which also shortens the body from 272 to 264
bytes. Removing exactly those two words from the original body yields a byte
sequence identical to the compiled output. This is a toolchain gap, not a source
shape question: the original image contains no adjacent pair of floating-point
multiplications anywhere (218 places separate such a pair with an empty word),
and the same gap already blocks the reviewed functions `func_800151C0`,
`func_800153C0` and `func_80017FD0`. Compiler flag variations (ISA level,
optimisation level, back-end and optimiser options) and the alternative
compiler release were tried and none restores the spacing.
