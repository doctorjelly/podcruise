# func_80098044 — tail of the signal processor's boot program, not a function

## Verdict

Not a function, and not main-processor code. `0x80098044` is the last stretch
of one 208-byte program written for the signal processor and stored in the main
image so the main processor can hand it to that processor as the boot loader of
every signal-processor task.

The true unit is `0x80097FF0` .. `0x800980BF` inclusive — 0xD0 bytes, USA ROM
`0x98BF0` .. `0x98CC0`. The label scanner split it into three "functions"
(`func_80097FF0`, `func_80097FF8`, `func_80098044`) and left one trailing
padding word loose. It is one contiguous unit and belongs in the build as
transferred data. The full evidence is written up once, in
`func_80097FF8.md`; this file records what is specific to this label.

## Boundary

- Assigned: USA VRAM `0x80098044`, ROM `0x98C44`, 120 bytes. The disassembler's
  own summary already says the range does not return.
- Corrected: this label is offsets 0x54 .. 0xC7 of the unit
  `0x80097FF0` .. `0x800980C0`, with the unit's last word being the padding word
  at `0x800980BC` (offset 0xCC). The padding word is part of the payload, not
  slack after it: the transfer that copies the payload works in eight-byte
  units, 0xCC is not a multiple of eight and 0xD0 is, and the length the main
  processor computes for the transfer is 0xD0.
- The range's final instruction is the delay slot of a jump to a fixed offset in
  another processor's instruction memory. There is no return, no prologue and no
  frame anywhere in it.

## Why this label in particular cannot stand alone

- **It is entered by falling through.** The word at offset 0x50, immediately
  before it, is at once the delay slot of a return in the previous label and the
  target of a conditional branch in that same label. Control arrives here by
  falling off the end of `func_80097FF8`, never by a call.
- **It branches backwards out of itself.** A conditional branch two thirds of
  the way through jumps back into the middle of `func_80097FF8`, to the shared
  helper at unit offset 0x3C, and relies on a return address that a call
  *earlier in this same label* left pointing into this label's own poll loop.
- **Its loads use a pointer set in a third label.** Every descriptor read here
  is relative to a value established once, in the delay slot of the jump at unit
  offset 0x04 — inside `func_80097FF0`. Nothing here re-establishes it.
- **No caller.** Nothing in the USA image calls `0x80098044`, and the only
  stored copy of any address in this unit anywhere in the ROM is the constant
  `0x80097FF0`, held in the boot-program field of a statically initialised task
  descriptor at `0x8009A2D0`.

## Why it is signal-processor code and not main-processor code

Summarised here; argued in full in `func_80097FF8.md`.

- The status register it writes and reads is coprocessor-0 register 4. On the
  signal processor that is the status register, holding the halt, break and
  signal bits. On the main processor register 4 is Context, and writing a fixed
  bit pattern to it before trapping would be meaningless.
- The halt is reached deliberately, immediately after that status write, and the
  program continues at the following word when the host restarts the processor.
  On the main processor the same encoding is the divide-by-zero trap, which is
  never a planned destination and never resumes in place.
- Its other coprocessor accesses are the signal processor's transfer engine:
  local address, host address and length into registers 0, 1 and 2, register 5
  polled for room in the queue, register 6 polled until the transfer finishes,
  register 7 the semaphore, register 11 the display processor's status.
- Its descriptor reads are at 0x04, 0x18 and 0x1C past the literal 0xFC0 —
  addresses inside the signal processor's 4 KiB data memory, where the host
  deposits the descriptor. On the main processor 0xFC0 is unmapped.
- Its exits are fixed offsets into the signal processor's instruction memory.
- It contains no relocation pairs, which a payload copied into another address
  space cannot have and main-processor code in this image almost always does.

## Callers and callees

No callers. The "callee" the disassembler names is not a function of this
program; it is a call to instruction-memory offset 0x3C, the unit's own shared
helper, rendered as an absolute address.

## Globals and access widths

None in this program's address space. Three 32-bit reads from the signal
processor's data memory at fixed offsets from 0xFC0: the descriptor's flag
word, its data pointer and its data length.

## Recovered behavior of this stretch

Three arms, in the order they sit in memory.

- **Finish.** Writes the status register with the fixed pattern that clears one
  signal and raises two others, then halts the processor. That is how a task
  ends: the host sees the halt and the raised signals, and the very next word is
  padding, so when the host later restarts the processor execution resumes at
  the start-of-task arm below without the loader being reloaded.
- **Start of task.** Reads the descriptor's flag word. If the caller asked to
  wait for the display processor, it polls that processor's status until its
  transfer-busy indication clears, going through the shared helper on every pass
  so an abort request from the host is noticed promptly; the helper returns into
  the middle of the poll because the return address was set once by a call at
  the top of the loop. When the flag is clear, or once the wait is over, control
  reaches the data-load arm.
- **Data load.** Reads the descriptor's data pointer and data length, waits for
  room in the transfer queue, asks for that block to be copied into local data
  memory starting at offset zero, waits for the copy to finish, runs the shared
  helper once more, and jumps to the program-load arm at unit offset 0x08 — the
  stretch labelled `func_80097FF8`, which brings in the task's own program and
  starts it.

The cold-start entry at unit offset 0x00 also jumps into the start-of-task arm,
so a first task and a restarted task follow the same path from here on.

## Segmentation

Carry `0x80097FF0` .. `0x800980C0` as one binary or word-data subsegment of
0xD0 bytes with a symbol at each end, and retire all three function labels. The
end symbol is load-bearing: two main-processor call sites, at `0x80007140` and
`0x80084C3C`, form both addresses with relocation pairs and subtract them to
obtain the payload's length, which they then store into the task descriptor.

Flagged for the orchestrator: a second, much larger signal-processor image
begins immediately at `0x800980C0` and continues past the end of the current
`main` code segment at ROM `0x99000` into the `remainder` binary segment. It is
encoded with that processor's vector instructions, which the main-processor
disassembler renders as invalid words, and it needs its own classification pass.

## Status

Skipped. There is nothing to recover in C: this is a payload for a different
processor, so there is no compiler, no calling convention and no translation
unit involved. No source file was created; the correct disposition is a data
segment.
