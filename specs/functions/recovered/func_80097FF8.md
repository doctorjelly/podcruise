# func_80097FF8 — interior of the signal processor's boot program, not a function

## Verdict

The proposed reading is correct, and stronger than proposed. `0x80097FF8` is
not a function and is not main-processor code. It is the middle of a single
208-byte program written for the signal processor, stored in the main image so
that the main processor can hand it to that processor as the boot loader of
every signal-processor task.

The true unit is `0x80097FF0` .. `0x800980BF` inclusive — 0xD0 bytes, USA ROM
`0x98BF0` .. `0x98CC0` — which the label scanner has split into three
"functions" (`func_80097FF0`, `func_80097FF8`, `func_80098044`) plus one
trailing padding word. It is one contiguous unit and should be segmented as
transferred data, with symbols at both ends. See "Segmentation" below.

## Boundary

- Assigned: USA VRAM `0x80097FF8`, ROM `0x98BF8`, 76 bytes. That range is real
  in the sense that the disassembler stopped there, but it is not a function
  boundary: the range has no prologue, no callers, an entry that is jumped to
  from inside a sibling label, and an exit that jumps to a fixed address in
  another processor's instruction memory.
- Corrected: the enclosing unit is `0x80097FF0` .. `0x800980C0` (exclusive),
  0xD0 bytes. `func_80097FF8` occupies offsets 0x08 .. 0x53 of it.
- Immediately before the unit sit three padding words at `0x80097FE4`,
  `0x80097FE8` and `0x80097FEC`, aligning the image to a sixteen-byte boundary.
  The last real main-processor function before them, `func_80097F60`, ends at
  `0x80097FE3` and is already recovered as C. Nothing executable is stranded.
- Immediately after the unit, at `0x800980C0`, a *different* signal-processor
  image begins. It is not part of this one.

## How the extent was established

Three independent lines of evidence agree on `0x80097FF0` as the base and
0xD0 as the length.

1. **Two link-time subtractions in main-processor code.** At `0x80007140` and
   again at `0x80084C3C`, main-processor code forms the address of
   `0x80097FF0` and the address of `0x800980C0` with high/low relocation pairs
   and subtracts one from the other. The difference is 208. Both sites then
   store the start address into offset 0x08 of a structure and the difference
   into offset 0x0C of the same structure. Taking an address with a relocation
   pair and computing a length from a second symbol is what you do to a data
   object, never to a function.
2. **A statically initialised descriptor in the ROM.** At `0x8009A2D0` the
   image already contains a filled-in structure whose field at offset 0x08 is
   the constant `0x80097FF0`, whose field at offset 0x10 is a pointer to a
   different image, and whose field at offset 0x18 is a pointer to a block of
   data. A scan of every word of the USA ROM finds this to be the *only* place
   where `0x80097FF0` is stored as a constant, and no branch or call anywhere
   in the image targets the address. The structure's field layout — type,
   flags, boot-program pointer, boot-program length, program pointer, program
   length, data pointer, data length — is the platform's signal-processor task
   descriptor, and offset 0x08 is its boot-program field.
3. **Three self-consistency checks inside the image itself.** The image
   contains three transfers to fixed addresses in the window that maps the
   signal processor's instruction memory: two jumps and one call, at instruction
   memory offsets 0x64, 0x08 and 0x3C. If, and only if, the image is loaded at
   instruction-memory offset zero, those offsets land on `0x80098054`,
   `0x80097FF8` and `0x8009802C` in the stored copy — and all three are
   meaningful destinations there: the start-of-task arm, this label's own
   entry, and the shared helper. Any other base makes all three land on
   nonsense simultaneously.

## Why the three labels are one program

- The data-memory pointer used by every load in the unit is established once,
  in the delay slot of the first label's jump at offset 0x04, and is read at
  offsets 0x08, 0x64, 0x8C and 0x90 — that is, in all three labels. Nothing
  re-establishes it.
- The value used as the final jump destination in `func_80097FF8` is computed
  eleven instructions earlier, in the same label, and doubles as the transfer's
  destination address. It is not a return address.
- A conditional branch near the end of `func_80098044` jumps *backwards* into
  the middle of `func_80097FF8`, to the shared helper at offset 0x3C.
- The word at offset 0x50 is simultaneously the delay slot of the helper's
  return and the target of the helper's own conditional branch. A compiler
  never produces that overlap; a person writing assembly by hand does.

## Why this cannot be main-processor code

- The pointer used for every descriptor load is the literal 0xFC0, and the
  loads read at 0x04, 0x10, 0x18 and 0x1C past it. Those are addresses inside
  the signal processor's 4 KiB data memory, which is exactly where the host
  deposits the task descriptor. On the main processor, 0xFC0 is a low unmapped
  address and the first load would fault before anything else happened.
- Coprocessor-0 register numbers 0, 1, 2, 4, 5, 6, 7 and 11 are used, and their
  use matches the signal processor's control block exactly: 0 and 1 receive the
  local and host addresses of a transfer, 2 receives its length, 6 is polled
  until the transfer completes, 5 is polled for room in the transfer queue, 4 is
  the status register, 7 is the semaphore, and 11 is the display processor's
  status. On the main processor those numbers are Index, Random, EntryLo0,
  PageMask, Wired, BadVAddr(reserved), Context and Config, and the code's
  central idiom — "poll register 6 until it reads zero, then start work" —
  is meaningless against Wired.
- The transfer targets are in the window that addresses the signal processor's
  instruction memory, not anywhere in this program.
- The unit contains no relocation pairs at all. Every constant is absolute and
  every jump target is a fixed instruction-memory offset. Main-processor code in
  this image uses relocation pairs constantly; a payload that will be copied
  into a different address space cannot.

## Attempts to falsify the reading

Four alternative readings were tested and each fails on evidence already listed.

- *Exception or trap code copied elsewhere at run time.* Would be moved by a
  copy loop with a length; instead the address goes into a descriptor field
  whose sibling field takes the length, and the coprocessor register numbers
  would still be wrong.
- *Ordinary main-processor code reached through a function pointer.* The
  whole-ROM word scan finds exactly one stored copy of the address, inside a
  descriptor, not a dispatch table, and the surrounding fields are a length and
  two more pointers.
- *Three separate signal-processor routines.* Falsified by the shared
  descriptor pointer, the backward branch across the label boundary, and the
  overlapped delay slot.
- *The image begins somewhere other than `0x80097FF0`.* Falsified by the two
  subtractions and by all three instruction-memory offsets resolving correctly
  only at that base.

## Callers and callees

No callers. The disassembler lists a callee `func_8400103C`; that is not a
function in this program, it is instruction-memory offset 0x3C — a call inside
the image to its own helper, rendered as an absolute address by the
disassembler.

## Globals and access widths

None in this program's address space. All loads are 32-bit reads from the
signal processor's data memory at fixed offsets from 0xFC0.

## Recovered behavior

The unit is the small loader that the signal processor runs before, and after,
every task. The main processor points the task descriptor's boot-program field
at it, starts the signal processor at instruction-memory offset zero, and this
program does the rest.

- **Entry.** Sets up the pointer to the task descriptor in local data memory
  and transfers to the start-of-task arm.
- **Start of task.** Reads the descriptor's flag word. If the caller asked to
  wait for the display processor, it repeatedly checks the display processor's
  status until its transfer-busy indication clears, re-entering the shared
  helper on every pass so that an abort request is noticed promptly. Then it
  reads the descriptor's data pointer and data length, waits for room in the
  transfer queue, requests that block be copied into local data memory starting
  at offset zero, waits for the copy to finish, runs the helper once more, and
  transfers to the program-load arm.
- **Program load (this label).** Reads the descriptor's program pointer and
  requests 3968 bytes be copied from there into local instruction memory
  starting 128 bytes in — filling instruction memory exactly to its end, since
  the first 128 bytes are this loader. It waits for the copy to complete, runs
  the helper, releases the semaphore and jumps to the freshly loaded program.
- **Shared helper.** Reads the status register and tests one signal bit. If the
  host has raised it, the helper does not return: it falls into the finish arm.
  Otherwise it releases the semaphore and returns.
- **Finish.** Writes the status register with the fixed pattern that clears one
  signal and raises two others, then halts the processor. Halting is how a task
  ends; the host observes the halt, and when it restarts the processor
  execution resumes at the word after the halt, which is the padding word
  immediately ahead of the start-of-task arm. The loader therefore re-enters
  itself cleanly on the next task without being reloaded.

Both round-trips through the loader — cold start and restart after a halt —
converge on the same start-of-task arm, which is why the entry jump and the
post-halt fall-through go to the same offset.

## Segmentation

The unit should be carried as transferred data, not as disassembled functions.
Concretely, for each version:

- Retire the three labels `func_80097FF0`, `func_80097FF8` and `func_80098044`.
- Emit `0x80097FF0` .. `0x800980C0` as one binary or word-data subsegment,
  0xD0 bytes at ROM `0x98BF0`, and keep a symbol at each end. Both ends are
  load-bearing: two main-processor call sites subtract them to obtain the
  length, so an end symbol at `0x800980C0` must exist and must not be folded
  into whatever follows.
- The three padding words at `0x80097FE4`..`0x80097FEF` belong to the alignment
  before the payload, not to it.
- The payload contains no relocations, so a byte-for-byte data emission is
  exact in every version.

One consequence worth flagging to the orchestrator, outside the scope of this
body: the material starting at `0x800980C0` is a second, larger
signal-processor image — the same descriptor's program field points at it for
one task type — and it is encoded with that processor's vector instructions,
which the main-processor disassembler renders as invalid words. It runs past
the end of the current `main` code segment at ROM `0x99000` and continues
inside the `remainder` binary segment, with what looks like the end of an image
near VRAM `0x800990CC`. The present segment boundary therefore cuts a microcode
image in half, and that region needs its own classification pass.

## Status

Skipped. No C source can produce these bytes, and the question does not really
arise: this is not main-processor code at all, so there is no compiler, no
calling convention and no translation unit to reproduce. No source file was
created, and none should be. The correct disposition is a data segment.
