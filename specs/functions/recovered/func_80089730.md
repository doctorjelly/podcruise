# func_80089730

## Boundary

USA: VRAM 0x80089730-0x80089787 inclusive, 88 bytes, ROM 0x8A330.
The body closes with a return whose delay slot is a no-op; two alignment
no-ops follow before the next routine. Both direct callers target 0x80089730,
the preceding routine (func_80089670) returns before this entry, and there
are no internal branches, so the assigned boundary is correct.

## Callers

Two direct call sites in the same routine, near 0x800083A8 and 0x80008498.
One masks a value to eight bits before the call and the other loads an
unsigned byte, so the second argument is a byte-wide quantity.

## Callees

- func_8008FC3C - posts a notice to a queue, exactly as for func_80089670;
  it copies sixteen bytes out of the supplied notice record.

## Globals

None referenced directly.

## Owner object fields used

- offset 0x14 - the notice queue; its address is handed to the callee.
- offset 0x3C - a signed 32-bit index, read once.
- offset 0x40 - a pointer to an array of 48-byte records, read once.

## Notice record fields written

- offset 0x00 - 16-bit code, set to the literal 2.
- offset 0x04 - pointer to the selected 48-byte record.
- offset 0x08 - 8-bit payload, taken from the second argument.

## Regional addresses

| version  | entry      | ROM     | queue helper   |
|----------|------------|---------|----------------|
| USA      | 0x80089730 | 0x8A330 | func_8008FC3C  |
| Japan    | 0x8008A420 | 0x8B020 | func_8009092C  |
| Europe   | 0x8008EC80 | 0x8F880 | func_8009518C  |

All three regional bodies were read independently and share the USA body's
frame, notice offsets and address arithmetic.

## Recovered behaviour

Identical in shape to func_80089670: it caches the owner's record-array base,
builds a notice naming the record designated by the owner's current index,
stamps it with the code 2 instead of 3, stores the caller's payload as a
single byte instead of a halfword, and posts it to the owner's queue with a
zero deadline.

## Compiler notes

Same translation unit and same -O3 requirement as func_80089670; see that
specification for why. One further source fact is forced here: the payload is
written to the notice *before* the record pointer, not after. With the two
stores in field order the code is still the right length but the scheduler
places the record-array load and the argument setup differently. Writing the
code, then the payload, then the record pointer reproduces the original
exactly. The sibling func_80089610 keeps the payload store last, so the two
were genuinely written in different orders.

## Status

Exact in USA, Japan, Europe and lrg_rev1, under the accepted profile with
-O3 in place of -O2.
