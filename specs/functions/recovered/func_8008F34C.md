# func_8008F34C

## Boundary (corrected)

- Assigned size 44 is wrong. The conditional branch at 0x8008F368 jumps over
  the return at 0x8008F370 into the label the scan calls `func_8008F378`, and
  that label has **zero** direct call sites anywhere in the image. It is an
  internal branch target, not a function.
- Corrected USA VRAM range: 0x8008F34C .. 0x8008F3F8 inclusive
  (0xB0 = 176 bytes, 44 instructions).
- USA ROM offset: 0x8FF4C.
- Terminates with a return whose delay slot is empty; the next real function
  begins at 0x8008F3FC with its own frame set-up.
- With the correction the function makes no calls at all, so the two stores
  into the incoming argument save area near the entry can only be parameter
  home-slot stores.

## Callers and callees

- Two direct call sites in the USA build, at 0x8008F69C and 0x8008F6C4. Both
  sit in the same caller, each converts a signed 16-bit field of a record to a
  float for the floating-point argument, passes a whole word plus a signed and
  an unsigned 16-bit field of the same record, and truncates the returned float
  back into the 16-bit field it started from.
- No callees after the boundary correction.

## Parameters

Four: one single-precision float, one 32-bit signed integer, one signed 16-bit
value and one unsigned 16-bit value. The two 16-bit parameters are normalised
on entry (sign extension and zero extension respectively) and each leaves a
dead home-slot store, which is what fixes their widths.

The float arrives in the first floating-point argument register while the three
integer parameters occupy the first three integer argument registers, yet the
two home-slot stores land at the third and fourth argument offsets. That
combination means the float consumes an argument *slot* without consuming an
integer argument *register*. See the calling-convention note below.

## Recovered behavior

Applies a fixed-point decay ratio to a value a chosen number of times.

The integer parameter is first divided by eight (an arithmetic shift right of
three); the low three bits are therefore flags belonging to the caller and are
discarded here. If nothing is left the input value is returned unchanged.

Otherwise the two 16-bit parameters are read as the halves of a 16.16
fixed-point ratio: the signed half is shifted up sixteen places and converted,
the unsigned half is converted as an unsigned quantity, the two are added and
the sum is divided by 65536, producing the ratio as a float.

The ratio is then raised to the remaining count by binary exponentiation. A
running product starts at one; the count is consumed one bit at a time from the
bottom, the running product is multiplied by the current factor whenever the
inspected bit is set, and the factor is squared for the next bit. The loop
stops as soon as the count reaches zero, and is additionally bounded to
thirty-two passes. The function returns the input value multiplied by the
running product.

The unsigned conversion of the low half is worth recording: an unsigned 16-bit
parameter converted to float produces the compiler's full unsigned-to-float
sequence, including the never-taken 2^32 correction, because in this compiler's
promotion rules an unsigned short widens to unsigned int rather than to int.

## Why this is not yet byte-exact

The recovered source compiles to exactly 176 bytes and, after renaming the
argument registers by one position, is instruction-for-instruction identical to
the ROM body: same order, same scheduling, same floating-point registers, same
branch-likely form, same placement of both filler words. Twenty-two of the
forty-four words differ and every one of them differs only in an argument
register field.

The local toolchain reserves the first integer argument register when the first
argument is a float, so the three integer parameters land one register higher
than in the ROM while the stack home offsets stay the same. The ROM's
translation unit packs integer arguments from the first integer argument
register while still charging the float a stack slot. No parameter order,
declaration style or flag reproduced it. Tried and rejected:

- float first, float second, float last, and float as a fifth argument;
- old-style (K&R) parameter declarations, with and without `-float`
  (these promote the float to double, adding a conversion at the return);
- `-xansi`, `-ansi`, `-cckr`, `-fullwarn`, `-32`, `-mips1`;
- the 7.1 compiler profile (different scheduling, 164 bytes).

This looks like a translation-unit level toolchain difference in the same
region that already forced `-O1` on `func_8008D420`, not a source-shape
question. Worth revisiting once the region's real compiler settings are known.
