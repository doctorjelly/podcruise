# func_800228C0

## Verified facts

- The canonical USA body begins at VRAM `0x800228C0`, ROM `0x234C0`, and
  ends after the `jr ra` delay slot at `0x8002406C`. Its size is `0x17B0`
  (6,064) bytes; the delay slot restores the `0x1F0`-byte stack frame and
  `func_80024070` begins at `0x80024070`.
- The only direct USA caller is `func_8004A880`. State 5 first calls
  `func_8004A7F8` for the controller object, then passes that same object to
  this routine.
- The function has no indirect jump or jump table. Its 33 static calls cover
  result transitions, save-data progression, sprite placement, formatted
  text/time drawing, a notification sound, and input feedback.
- The recovered controller offsets agree with `func_8004F358`; candidate
  result stride `0x88`, stage/save record fields, and the save table at
  `D_80113680` agree with `func_800280D8` and neighboring recovered users.
- The caller mappings identify JP `func_80022D60` and EU `func_80023F68` as
  structural regional equivalents. They were used only to confirm the
  corresponding caller position and relocation pattern.

## Behavioral specification

Maintain and draw the post-race standings screen. On first entry, identify the
current event, sanitize each recorded final and segment time, sort the result
pointers by placement, and calculate the best positive segment value for each
local player. If a new player record requires a transition, select that player
and return through the result-state controller.

Otherwise, copy improved records and their three-byte profile labels into save
data. In the single-player special mode, fold tied final times to the same
placement, award any newly earned unlock and currency, update event-completion
bitfields, advance the selected event where appropriate, and persist the
largest four progress bytes.

Every frame, expire the result notification timer, draw the visible ranked
rows with edge fading, distinguish the local-player rows by color and profile
label, and display a currency award when present. Process each local
controller's confirmation and vertical axis, clamp the scroll offset to the
result list, expose whether more rows exist above or below, and request the
next controller state when confirmation has selected an exit.

## Recovery notes

- Candidate pointers are kept both in original player order for record tests
  and in `D_800D73A8` placement order for display. Sorting the local array
  would change the two-player winner comparisons.
- Candidate `+0x5C` is loaded as a halfword for sorting and the primary rank;
  the second local rank is read from byte `+0x5D`. The C conversion preserves
  the low signed byte without inventing a semantic field name.
- The reward lookup is an overlapping view at
  `owner + 0x88 + owner[0x90] * 8 + rank * 2`; it is intentionally expressed
  by byte offset instead of pretending the selection byte and table are
  independent non-overlapping structure members.
- `func_8000A920` takes two arguments, `func_8002D4C4` takes one, and
  `func_800399F0` takes none. Live argument registers at those call sites do
  not enlarge their verified callee contracts.
- The USA assembly's no-effect `D_800A4BE0` count loop is retained as a debug
  timing path. All meaningful branch-likely delay-slot actions were expressed
  in their corresponding C branches.

## Status

**Behavior-recovered C, not byte-matching.** Exact isolated comparisons were
run against the canonical USA bytes. IDO 5.3 emits a 6,000-byte function and
IDO 7.1 emits 5,952 bytes, versus the 6,064-byte original; both first differ at
byte `0x2`. The IDO 5.3 candidate has the same 33 call targets in the same
static order, but broad instruction and register-allocation differences remain.
The USA split must therefore continue to assemble the original body.
