# func_80096E90

## Boundary

USA VRAM 0x80096E90-0x800973F8, ROM 0x97A90, 1384 bytes (346 instructions).
The assigned boundary is correct and was confirmed four ways:

1. The body ends with a return whose delay slot is empty and whose preceding
   instruction releases the 0x18-byte frame the first instruction reserved, so
   the frame is balanced across the whole label.
2. Every branch target inside the body lies between the entry and that return.
   Nothing jumps past the return, and no interior label has an outside entry,
   so this is not a merged pair of functions and not a shared tail.
3. Both direct calls in the ROM target the entry address exactly. There is only
   one call site; the second hit is the same site listed under a duplicated
   split file.
4. The preceding function ends with its own complete return sequence eight
   bytes earlier, and those eight bytes are alignment padding, so nothing falls
   through into this label.

The label scan was right about the extent here, which is unusual for a body
this size, so the extent needs no correction.

## Why this was never attempted, and why it is not hand-written

The body reads five values that were never written inside it, three of them in
callee-saved registers, and it destroys those three registers without ever
restoring them. That is why it was set aside as hand-written assembly. It is
not. It contains no privileged instruction, no cache operation, no kernel
register, no trapping arithmetic and no unpaired partial-word access; every
instruction in it is ordinary compiler output.

The explanation is the one already established for this ROM: the translation
unit was built one optimisation level above the rest of the game. At that level
the compiler allocates registers across the whole unit at once, so a file-local
routine takes its arguments wherever the allocator wanted them and clobbers
callee-saved registers its caller will not need again. Written as a file-local
function beside a caller and compiled at that level, this source reproduces the
frame, the length (1384 bytes exactly), all five parameter registers, both
narrowing shift pairs, all three home-slot stores and 336 of the 346
instructions byte for byte.

Three independent facts pin the parameter list:

- The three stores made in the prologue land four, twelve and sixteen bytes
  above the incoming stack pointer. Those are the home slots of parameters two,
  four and five, which fixes the arity at five and the positions of the three
  parameters the function overwrites.
- Parameters four and five are immediately widened from sixteen bits with a
  signed shift pair, so both are signed sixteen-bit values; the single caller
  loads one of them from its own frame with a signed halfword load.
- Parameter two is immediately masked to eight bits and the caller loads it
  with an unsigned byte load, so it is an unsigned eight-bit value.

## Callers

One direct call, from func_80097400 (USA 0x8009791C). That caller materialises
all five inputs immediately before the call - object pointer and conversion
letter from its own frame, digit pointer from a register it was already walking,
significant-digit count already live, exponent from a signed halfword in its
frame - and returns immediately after, restoring its own saved registers from
its own frame rather than from the home slots this function writes.

## Translation-unit layout (confirmed by construction)

The original unit is laid out as: this function's out-of-line body (1384
bytes), then an eight-byte do-nothing body at 0x800973F8, then func_80097400.
That eight-byte body is not a real function and has no callers: it is what the
compiler leaves behind for a second file-local routine that it inlined into its
only call site. Compiling this source together with a stand-in caller and one
additional tiny file-local helper that the caller uses once reproduces that
layout byte position for byte position - 1384 bytes, then eight bytes, then the
caller. Anyone continuing this work should expect the recovered unit to contain
three source functions, not two.

## Globals and access widths

One global: D_800AE1C0, a two-byte constant string holding the single character
zero. It is used only as the substitute digit string when the caller supplies no
significant digits, and it is read one unsigned byte at a time.

The object passed in as parameter one is used at these offsets, all as 32-bit
words except the buffer contents:

- 0x08 pointer to the output character buffer; the buffer itself is written one
  byte at a time and read never.
- 0x0C, 0x10 leading group length and leading zero-fill count. Only the zero-fill
  count is written, and only by the padding step at the end.
- 0x14, 0x18 middle group length and the zero-fill count that follows it.
- 0x1C, 0x20 trailing group length and the zero-fill count that follows it.
- 0x24 precision, read and written throughout.
- 0x28 field width, read once by the padding step.
- 0x30 flag word; bit 3 is the "keep the point" flag, and the padding step runs
  only when bits 2 and 4 of that word are, respectively, clear and set.

Offsets 0x00-0x07 and 0x2C are untouched here.

## Recovered behaviour

The function lays out the digits of an already-converted floating-point value
into the caller's output buffer and records, in the caller's own bookkeeping
object, how many characters belong to each of three groups and how many zeros
have to be generated between them. It writes only the characters that are not
runs of zeros; the runs are recorded as counts so the caller can emit them
without buffering.

Its inputs are the bookkeeping object, the conversion letter the user asked
for, a string of significant digits, how many of those digits are significant,
and the decimal exponent of the first digit. If there are no significant
digits it substitutes the single character zero and treats that as one
significant digit.

It first decides between fixed-point and scientific layout. Fixed point is used
when the letter is the fixed-point one, and also for the general-purpose
letters when the exponent lies between minus four and the requested precision.
Everything else, including both explicit scientific letters, uses scientific
layout.

**Fixed-point layout.** The exponent is advanced by one so that it counts the
digits belonging before the point. For the general-purpose letters the
precision is first reduced to the number of significant digits unless the
keep-the-point flag is set, then reduced by the digit count before the point,
and clamped at zero, so that the precision once again means "digits after the
point".

Three cases follow.

If nothing belongs before the point, a single zero digit is written, then a
decimal point if the precision is positive or the keep-the-point flag is set.
The leading zeros after the point are the negated exponent, clamped so they can
never exceed the precision; that count is recorded as the middle zero run, and
the precision is reduced by it. At most that many significant digits are then
copied, recorded as the trailing group, and any precision left over becomes the
trailing zero run.

If there are fewer significant digits than digits before the point, all of them
are copied and recorded as the middle group; the shortfall becomes the middle
zero run - the zeros that pad the number out to the decimal point. A decimal
point is appended, and counted in the trailing group, when the precision is
positive or the keep-the-point flag is set, and the whole precision becomes the
trailing zero run.

Otherwise the digits split across the point: the ones before it are copied
first, then a point if the precision is positive or the keep-the-point flag is
set, then as many of the remaining digits as the precision allows, and any
unused precision becomes the middle zero run.

**Scientific layout.** For the general-purpose letters the precision is first
reduced to the significant-digit count if it is larger, then reduced by one
(because one digit sits before the point) and clamped at zero, and the letter is
replaced by its explicit scientific equivalent of the same case.

One digit is written, then a point if the precision is positive or the
keep-the-point flag is set. When the precision is positive, one digit is
discarded from the significant count and at most precision-many of the rest are
copied; whatever precision is left over becomes the middle zero run.

The exponent field follows: the letter, then a sign, then the exponent in
decimal. The exponent is negated if it was negative. It is printed with a
thousands digit only if it reaches one thousand and a hundreds digit only if it
reaches one hundred, and always with a tens and a units digit, so the field is
never shorter than two digits. The whole exponent field is recorded as the
trailing group.

**Zero padding.** Finally, if the flag word asks for zero padding and not for
left alignment, the five recorded counts are summed and, if the total is
narrower than the requested field width, the difference is recorded as the
leading zero run.

## Status

Behaviour recovered and reviewed. Not byte-exact: 1085 of the 1384 bytes are
identical from the entry, and 336 of the 346 instructions are identical
including every register assignment. The ten that differ are all inside the
three integer-division blocks that print the exponent digits, and they are one
scheduling decision repeated three times:

- In each block the original places the first half of the shift pair that
  narrows the remainder between the two instructions that read the division
  result, while this build places the second division-result read there
  instead. The instruction counts are equal; only the order differs.
- In the first two of those blocks, the original writes the narrowed remainder
  back to the exponent before storing the digit, and this build stores the digit
  first. The third block agrees with the original because the data flow there
  forces the order.

The cause is a tie in the block scheduler that is broken by source order: the
original unit evaluates the remainder before the quotient, which cannot be
written in C without keeping a copy of the pre-division exponent. Every way of
introducing that copy was tried and each is worse: an integer temporary for the
quotient displaces the divisor into a different register and moves the first
difference 60 bytes earlier; a sixteen-bit temporary adds a second narrowing
shift pair; and keeping a copy of the exponent itself defeats the
quotient/remainder pairing and emits two divide instructions per digit.

Ruled out as causes: the multiply workaround flag (removing it changes nothing),
the compiler version (7.1 diverges after five bytes), the shape of the stand-in
caller (three quite different callers give identical bytes for this body), the
placement of the pointer increment relative to the store, and writing the
constant on the left of the addition.
