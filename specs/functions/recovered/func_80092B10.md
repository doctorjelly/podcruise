# func_80092B10

## Boundary

USA VRAM 0x80092B10-0x8009317F inclusive, ROM 0x93710, 1648 bytes,
412 instructions. The assigned boundary is **correct**; four independent
checks agree.

1. The body ends with a return whose delay slot is a no-op, immediately after
   the frame release. Nothing follows before the next function.
2. The preceding function (func_800928F0) ends with its own complete return
   sequence at 0x80092B04/0x80092B08, and a single padding no-op at
   0x80092B0C aligns this entry to eight bytes. No branch of the preceding
   function reaches past its own return.
3. The one direct call site targets 0x80092B10 exactly.
4. The body dispatches through a 52-entry table of code addresses at
   0x800AE034. Every one of those 52 addresses lies inside
   [0x80092B10, 0x80093180); none escapes the label. The apparent "extra
   entry points" that make this body look hand-written are simply that table's
   targets.

Frame: 24 bytes - sixteen bytes of outgoing-argument space, one slot for the
return address at +0x14, and four bytes of padding. No callee-saved register
is saved or restored.

## Why it looked hand-written, and why it is not

The body reads a callee-saved register as an incoming pointer without ever
writing it, and it takes its remaining three inputs in the second, third and
fourth argument registers rather than the first three. That is the signature
of a file-local routine in a translation unit built one optimisation level
above the rest of the ROM, where the compiler allocates registers across the
whole unit at once: the routine gets its inputs wherever the allocator wanted
them and is emitted with no symbol of its own. Compiling an ordinary static C
function of this shape at that level reproduces the register assignment, the
frame, the dead home-slot store of the third parameter, the switch dispatch
and the jump table exactly. Nothing here is outside what the compiler emits:
there is no coprocessor-0 transfer, no cache instruction, no use of the
kernel-reserved registers, no trapping arithmetic and no unpaired partial-word
access.

The dead store of the third input into its stack home slot, never read back,
pins that parameter as a byte-wide value; the byte mask applied to it before
use pins it as unsigned.

## Callers

One direct call, from func_80093180 (the format-string driver) at 0x8009345C.
That caller sets up all four inputs immediately before the call: a pointer to
a 56-byte working record it keeps in its own frame at +0xA0, a pointer to its
own saved argument-list cursor at +0xE4, the conversion letter freshly loaded
as an unsigned byte from the format string, and a scratch character buffer at
+0x74. It consumes no return value; this routine returns nothing.

## Recovered behaviour

The routine converts one format conversion into the caller's scratch buffer
and record, then hands off to a renderer.

It first clears the six length and zero counts in the record. It then
dispatches on the conversion letter.

- **Character.** Fetch one integer-sized argument, store its low byte at the
  end of the prefix, and count it.
- **Signed decimal** (two letters). Fetch the argument as a 32-bit value for a
  bare or 'l'-modified conversion, or as a 64-bit value for 'L', and widen it
  by its sign into the record's 64-bit slot. If the modifier is 'h', narrow it
  to a signed 16-bit value and widen it again. Then, if the value is negative,
  place a minus sign; otherwise if the plus flag is set, place a plus sign;
  otherwise if the space flag is set, place a space. Point the record's text
  start at the current end of the prefix and call the integer renderer with
  the same letter.
- **Unsigned decimal, octal and both hexadecimal cases** (four letters). Fetch
  the argument the same way as above. Then, if the modifier is 'h', reduce the
  value to its unsigned 16-bit part; if there is no modifier, reduce it to its
  unsigned 32-bit part; a 'l' or 'L' modifier leaves it alone. If the
  alternate flag is set, place a zero digit, and for either hexadecimal letter
  place that letter after it. Point the record's text start at the current end
  of the prefix and call the integer renderer.
- **Floating point** (five letters). Fetch an eight-byte argument - the same
  fetch on both the 'L' and the non-'L' path. Then, if the value's sign bit is
  set, place a minus sign; otherwise apply the plus and space flags exactly as
  for signed decimal. Point the record's text start at the current end of the
  prefix and call the floating-point renderer.
- **Count.** Fetch a pointer argument and store the driver's running character
  total through it: as a 16-bit value for 'h', a 32-bit value for 'l', none or
  anything else, and as a zero-extended 64-bit value for 'L'.
- **Pointer.** Fetch a pointer argument, widen it by its sign into the
  record's 64-bit slot, point the record's text start at the current end of
  the prefix, and call the integer renderer as though the letter were a
  lowercase hexadecimal conversion.
- **String.** Fetch a pointer argument, record it as the text start, and set
  the body length to that string's measured length. If a precision was given
  and is smaller than that length, clamp the body length to the precision.
- **Percent sign.** Place a literal percent sign in the prefix and count it.
- **Anything else.** Place the conversion letter itself in the prefix and
  count it. Letters outside the dispatch table's range, and every unused entry
  inside it, land here.

Note that the argument fetch is aligned before every read: to four bytes for a
word-sized argument and to eight for a double or a 64-bit integer. The
eight-byte fetch in the original build carries two extra arms selected by the
low bits of the argument cursor; both are unreachable, because an argument
list is always at least word aligned, and both are reproduced here only
because the original build emits them.

All four bodies are 1648 bytes. lrg_rev1 is byte-identical to USA. Japan and
Europe differ from USA in exactly six words: the dispatch table reference and
the five call targets. Regional callee addresses are 0x800978E0, 0x800980F0
and 0x8008D00C for Japan, and 0x8009C140, 0x8009C950 and 0x8009186C for
Europe. No structural difference exists in any region.

## Status

Behaviour recovered and reviewed; not byte-exact. The rebuilt body is the
correct length (1648 bytes), lands at the canonical address, produces a
dispatch table whose 52 entries name the same case addresses as the original,
and matches 368 of 412 instructions byte for byte. The 44 that differ are all
register-naming choices in three places: which of two general registers holds
the argument cursor and its copy in the two eight-byte fetches, and which
scratch registers the count and pointer conversions rotate through. No
instruction differs in opcode, operand order, count or placement.
