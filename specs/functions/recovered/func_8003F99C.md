# func_8003F99C

## Boundary

- USA VRAM `0x8003F99C`..`0x8003FA23` (136 bytes, 34 instructions), ROM `0x4059C`.
- Ends with the return instruction followed by an empty delay slot; the frame
  teardown sits one instruction earlier because two exit paths share it.
- Boundary confirmed correct: the three internal labels are all branch targets
  within the range (two of them are the shared epilogue arms), and all direct
  call sites target `0x8003F99C`.

## Callers and callees

- 25 direct call sites in the USA build. Most sites build a small record on
  their own stack frame (a leading word plus a four-character tag such as the
  literals `Qery` and `Free`) and pass its address in the second slot, so the
  second parameter is a pointer to a short message record.
- One indirect callee: the handler taken from the matched descriptor record.

## Recovered behavior

The routine delivers a message to the handler that owns the given element.

A null element pointer is ignored outright. Otherwise the routine reads the
element's identifier and scans the null-terminated descriptor table for the
record carrying the same identifier. The scan stops at that record whatever
happens next: the routine never examines a second matching record.

Once the record is found, the message is delivered only when the record has a
handler and the element's flag word does not have bit 8 set. Bit 8 is the same
"unavailable" marker that the lookup routine uses to skip elements, and several
callers test it themselves before calling. When both conditions hold the
handler is invoked with the element pointer and the message pointer; the
message pointer is supplied twice, once in each of the handler's two message
argument slots. Nothing is returned.

## Compiler notes

The third handler argument is not cosmetic. The original spills the message
parameter to its incoming home slot and reloads it into an extra argument
register before the call; every two-argument formulation, and every variation
of parameter type, guard order, loop form and control flow that was tried,
keeps the message in a scratch register instead and produces different bytes.
Passing the message in both handler message slots is the only shape found that
reproduces the original instruction sequence exactly, and it is also the only
one consistent with the extra argument register being loaded at all.

## Status

Exact. Byte-identical in USA, Japan, Europe and lrg_rev1.
