# func_8008ABEC — 64-bit signed division helper

## Boundary
- USA VRAM `0x8008ABEC`..`0x8008AC47` (92 bytes), ROM `0x8B7EC`.
- Ends with `jr $ra` plus a delay-slot instruction producing the upper half of
  the quotient. Two internal forward branch targets exist inside the range
  (the trap-check join points); neither has a direct caller, and both are
  reached only from within this body, so they are not function starts.
- The single direct call site targets `0x8008ABEC`. Assigned boundary correct.

## Callers / callees
- One direct call site, inside `func_80097E60` (at `0x80097E80`).
- No callees; leaf function with no stack frame beyond the argument home slots.

## Globals
- None.

## Regional addresses
- Japan `0x8008B8DC` / ROM `0x08C4DC`.
- Europe `0x8009013C` / ROM `0x090D3C`.
- lrg_rev1 shares the USA address `0x8008ABEC` / ROM `0x8B7EC`.
- All three regional bodies were read independently and are identical to the
  USA body.

## Recovered behavior
Takes two 64-bit signed integers and returns the first divided by the second.

The body is the compiler's own division support routine, so besides the divide
it contains the two hardware trap checks the compiler always emits around a
64-bit divide: a trap when the divisor is zero, and a trap when the most
negative 64-bit value is divided by minus one. Both are generated by the
compiler from a plain `/`, not written in the source. As with the other 64-bit
helpers, the two arguments are re-assembled from their four argument words via
the caller-provided home slots and the quotient is split into halves to return.

## Build note
Same as `func_8008AB84`: needs the `-mips3 -o32` compile, otherwise IDO turns
the `/` into a call to this routine instead of emitting it.

## Status
Exact in USA, Japan, Europe and lrg_rev1.
