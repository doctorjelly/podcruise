## Recovered behavior

Reports whether the serial interface is currently occupied. It reads the
interface's status register once through the uncached address window, keeps the
low two flag bits (a transfer in progress and a register access in progress),
and returns 1 if either is set and 0 otherwise. It has no arguments and no side
effects; the read must not be folded away or duplicated, so the register is
addressed as volatile.

## Compiler profile finding

This body does not come out of the accepted ido53_o2 profile. Under -O2 the
compiler needs no stack frame here, merges the two returns, and emits 36 or 40
bytes; the original reserves an eight-byte frame it never stores into, keeps a
single exit that releases the frame, and is 44 bytes.

Compiled at -O1 (same compiler, same remaining flags: `-G 0 -O1 -mips2
-non_shared -Xcpluscomm -signed -Wab,-r4300_mul`) the recovered C is
byte-identical in all four versions. The source form that matches also needs the
status value held in a variable declared with `register`; reading the register
straight into the expression, or dropping `register`, is four bytes short at
-O1.

The neighbouring hardware-poll routines look like the same translation unit:
`func_80093A60` (graphics-pipeline busy check, 44 bytes, same shape) also
matches its committed source exactly at -O1 while failing at -O2, and
`func_8008D420` has the same never-stored eight-byte frame. This is evidence for
a small group of low-level polling routines built at a lower optimisation level
than the rest of the image, and it is worth an `ido53_o1` profile entry in the
shared matching configuration rather than a per-function workaround.

## Status

Behavior recovered, and byte-identical under an ido53 -O1 profile in USA, Japan,
Europe and lrg_rev1. Not matching under the accepted ido53_o2 profile.
