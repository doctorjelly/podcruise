# Bootstrap state accessors

Status: **behavior recovered; exact C byte match unverified**.

These specifications contain independently stated behavior and compact address
facts. They do not reproduce disassembly or decompiler output.

## Shared evidence

- Each candidate is exactly 12 bytes in the USA ROM.
- Each has a unique 32-instruction structural-window match in Japan and Europe.
- Each remains at the same ROM offset and VRAM address in all three retail
  builds.
- `analysis/bootstrap_functions.json` records SHA-256 hashes of each 12-byte
  range; it records no instruction bytes.

## `func_80000520`

- USA VRAM: `0x80000520`
- USA ROM: `0x001120`
- Input: one 32-bit value in the first integer argument position.
- Observable effect: write that value to the 32-bit global at `0x8009A270`.
- Return value: none observed.

## `func_8000052C`

- USA VRAM: `0x8000052C`
- USA ROM: `0x00112C`
- Input: none observed.
- Observable effect: write zero to the 32-bit global at `0x8009A280`.
- Return value: none observed.

## `func_80000538`

- USA VRAM: `0x80000538`
- USA ROM: `0x001138`
- Input: none observed.
- Observable effect: none observed.
- Return value: the 32-bit value stored at global address `0x8009A280`.

## Why names remain autogenerated

The second and third functions resemble a reset/get pair, but the meaning of
the global is unknown. Naming them `ResetSomething` and `GetSomething` would
smuggle an unsupported semantic claim into the source. Autogenerated address
names are intentionally temporary.

## Matching gate

The C in `src/bootstrap_state.c` is the most direct expression of these
behaviors and passes a host syntax/warning check. It does **not** count as
matching until an IP-cleared exact IDO toolchain compiles each function to the
same 12 bytes in the canonical USA build.
