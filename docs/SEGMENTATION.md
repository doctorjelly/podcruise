# What counts as code, and what is excluded from decompilation

This file records which bytes of the USA retail image are decompilation work
and which are not, so that a coverage percentage has a denominator that can be
defended rather than one chosen for convenience.

## Summary

Main-processor text runs from ROM `0x1000` to ROM `0x98BE4` (VRAM `0x80000400`
to `0x80097FE4`): **621,540 bytes**. That interval is the denominator for
matching-C coverage.

Inside it, almost nothing is data. The bodies that a reachability scan flags as
unreferenced are **99.1% ordinary main-processor code**. Only 880 bytes are
not, and they sit in the final kilobyte of the segment.

| class | bodies | bytes | decompilation work? |
|---|---:|---:|---|
| CPU code, framed function | 175 | 86,144 | yes |
| CPU code, leaf function | 163 | 11,584 | yes |
| CPU code, reset entry stub | 1 | 112 | yes, boot path |
| label-scan artefact | 11 | 108 | no, a boundary fix |
| signal-processor microcode image | 1 | 384 | no, segment as data |
| signal-processor boot loader | 2 | 196 | no, segment as data |
| alignment padding | 75 | 300 | no |

There is no data table, string bank, jump table or asset payload anywhere in
the `main` segment. The program's 60 pointer tables — 927 entries, of which 857
are switch jump tables — all live in `.data` between ROM `0xA2BF4` and
`0xAED60`. The whole segment holds 620 bytes of zero padding and one 14-byte
build stamp. **The game's assets are outside this interval entirely**, so there
is no asset carve-out to take from the code denominator.

## Segment boundaries

| # | VRAM | ROM | contents | bytes |
|---|---|---|---|---:|
| 2 | `0x80097FE4` | `0x98BE4` | end of main-processor text, then alignment fill | 12 |
| 3 | `0x80097FF0` | `0x98BF0` | signal-processor boot loader | 208 |
| 4 | `0x800980C0` | `0x98CC0` | graphics microcode, program text | 4,096 |
| 5 | `0x800990C0` | `0x99CC0` | graphics microcode overlay — see below | 912 |
| 6 | `0x80099450` | `0x9A050` | audio microcode, program text | 3,616 |
| 7 | `0x8009A270` | `0x9AE70` | start of ordinary `.data` | — |

Boundary 3 is confirmed three independent ways: the length subtraction at
`0x80007140` and `0x800071C8`, the static task record at `0x8009A2D0`, and
`src/functions/func_80084C30.c`, which names it. Boundary 4 is named as
graphics microcode by that same recovered function, and its internal transfers
span instruction-memory offsets `0x008` to `0xFD8` — exactly filling IMEM.

## The old `0x99000` cut is wrong

The conservative first-pass interval ended at ROM `0x99000`. That lands **832
bytes inside** the 4,096-byte graphics microcode image. The half below the cut
transfers control to instruction-memory offsets in the half above it, and the
half above transfers back down to offset `0x008` — one program, with control
flow crossing the boundary in both directions, and no padding or change of
encoding at the cut. Any coverage figure computed against `0x99000` is
therefore measuring a denominator that splits a single program in two.

## Not expressible as C

Twenty-seven bodies totalling 4,332 bytes cannot be the output of any C
translation unit, and are listed with their decisive reason in
`analysis/non_c_functions.json` (generated by `make classify`). The reasons are
coprocessor-0 transfers, cache maintenance, use of the kernel-reserved
registers `$k0`/`$k1`, and one block that is the signal processor's own program
rather than main-processor code.

This is a capability limit, not an optimisation the compiler declined to make:
the accepted compiler has no inline assembly in any spelling. `asm`, `__asm`
and `__asm__` parse as calls to an undeclared function, `asm volatile` is a
syntax error, and `#pragma asm`/`#pragma endasm` emits nothing.

Unaligned word access, floating-point control transfers and 64-bit operations
are explicitly **not** reasons to retire a function; each was checked against
the compiler and each is reachable from ordinary C. Treating any of them as
decisive would retire recoverable functions, and had done so before this was
checked.

## Known measurement defect, now fixed

`analysis/generated/us/asm/` accumulates files from earlier splits. The
classifier used to glob that directory, and because it keys bodies by label and
appends, 205 bodies were measured two to four times over — inflating the
unreferenced set from its true 431 bodies / 98,840 bytes to 453 / 209,784. It
now takes its file list from `config/us.yaml` and also counts references from
recovered C. Any figure quoted from before that fix is roughly double the truth.

## What is still unsettled

The role of `0x800990C0`–`0x80099450` (912 bytes) is not established. It reads
either as an overlay for the graphics microcode or as a second, smaller image.
Both readings are consistent with the surrounding evidence, and the choice does
not move any coverage number, because the region is excluded from the code
denominator under either reading.

The length of the microcode data image at `0x800AE1D0` is also not established.

351 bodies (70,924 bytes) have no inbound reference anywhere in the 32 MB ROM.
Their class is certain — main-processor code — but their entry path is not.
Either further dispatch tables are built at run time or from compressed data,
or this is genuinely dead code retained by object-granularity linking. The two
readings agree on segmentation and differ only on what to decompile first.
